# Time Tracker (`tt`) - AI Assistant Guide

AI-native time tracker that passively collects activity signals from development tools and uses LLMs to generate accurate timesheets.

## The point: leverage

**Human attention is the scarce resource; agent time is cheap and parallelizable.** The product measures how much work you get per unit of your attention. Full statement in `specs/design/core-concepts.md`.

Two invariants follow, and they are not symmetric:

- **Direct time is exclusive.** Attention is singular, so `direct_ms` is the *union* of focus intervals. Total direct across all streams can never exceed wall clock.
- **Delegated time is concurrent.** Agents run in parallel, so `delegated_ms` is the *sum* across sessions. It routinely exceeds wall clock by 10x or more — a day with 24 wall-clock hours and 250 delegated hours is normal and correct.

Delegated time exceeding wall clock is **the leverage signal, not a bug**. Do not "fix" it by unioning, capping, or clamping delegated intervals, and do not report it as an anomaly. `tt-core/src/allocation.rs` has a regression test guarding this; if it fails, the change is wrong, not the test.

Corollary: never report a percentage of `direct + delegated`. They have no shared denominator — one is wall-clock hours, the other machine-hours. Report them separately plus the delegation ratio (`delegated ÷ direct`), which is what `tt report`'s SUMMARY does.

### "Where did my time go" always means direct time

Leverage is what the product *measures*; attention is what the user *budgets*. So when the user asks where their time went, or asks for a breakdown of a day or week, **answer in direct time** — that is a standing instruction, not a per-question preference. Delegated time is context on how far that attention reached, never the headline.

Direct time is therefore the primary axis of every human-readable view: sections are ordered by it, bars are scaled to it, and it is the figure on each row. Delegated time trails each row as a subordinate `+` figure so leverage stays visible without competing for the eye. `tt report`'s SUMMARY still reports Wall clock / Direct / Delegated / Leverage together, because that block is where the two quantities are meant to be compared.

Concretely, in `tt-cli/src/commands/report/render.rs`: BY STREAM and BY TAG both sort by `time_direct_ms` and scale their bars to it — to the largest **stream** or **tag**, deliberately excluding the `(unassigned)`/`(untagged)` rows. Those rows are the *absence* of a stream rather than one more of them, and including them in the scale collapsed every real row to the 1-block minimum the moment unassigned exceeded the top stream by ~10x, which is now the ordinary state: after the pane release the week of 2026-08-03 read 47h 26m unassigned against a top stream of 4h 17m, so BY STREAM printed `█░░░░░░░░░` on every line and compared nothing. `progress_bar` clamps a value above its max, so the remainder row still draws a full bar and is not visually understated; when *no* stream has direct time the remainder becomes the scale, since a zero max renders an empty bar and would draw the only row carrying time as if it carried none. Ordering or scaling either section by `direct + delegated` is a regression — a stream with 6 minutes of attention and 200 hours of agent time would take the top of the report and answer the wrong question. `report/render/tests.rs` guards the ordering, the scaling, and the presence of per-stream direct time.

Two consequences worth stating, because both look like omissions:

- **Rows with zero direct time collapse into one tail line** (`(+ 8 streams with no direct time, 143h 2m delegated)`). They are summarised rather than deleted, because their delegated time is real work the SUMMARY still counts; they are summarised rather than listed, because they answer the attention question with silence and would crowd out the rows that answer it.
- **`(unassigned)` stays a visible row of its own** even when its direct time is zero. Unattributed *direct* time is the signal that classification has fallen behind, so it must never be folded into a count.

## Injected text is not attention

Coding agents put everything on the user turn into the transcript as a user message, including text the harness wrote itself: background-task notices, `<pty_exited>` blocks, continuation directives, agent-to-agent notifications, compaction banners. A `user_message` event opens a 5-minute attention window exactly like a pane focus, so counting those fabricates direct time — they once filled a whole night with attention on a day nobody was awake.

`tt_core::injection::is_injected` is the single arbiter. **Every code path that turns a transcript message into a `user_message` must gate on it**, and there are three: `tt-core/src/opencode.rs`, `tt-core/src/session.rs`, and the independent Claude JSONL parser in `tt-cli/src/commands/export.rs`. Miss one and injections keep arriving from whichever machine uses that path.

The matching rule is a **denylist checked against the message's leading token** (after leading whitespace and Markdown rules). Both halves are load-bearing:

- *Denylist, not allowlist.* Injections are a closed set this harness emits; human prefixes grow with every new skill (`<skill-instruction>`, `[analyze-mode]`, `[CONTEXT]`, `<Work_Context>`, …). A shape rule like `<[a-z-]+>` silently deletes real intent, and under-reported attention looks like a quiet day rather than a bug.
- *Leading token, not substring.* A human quoting a marker — a bug report about this very code, a pasted transcript — contains it mid-body. Substring matching erases those messages.

Growing the list is expected. Verify the marker appears in real transcripts at the start of messages, add it to `INJECTION_MARKERS` with a comment naming its emitter, add a test, and re-run the remediation below so history follows.

### Crate Dependencies

```
tt-core     (no internal deps)
tt-db     ─> tt-core
tt-llm      (standalone: rig-core / Anthropic; no internal deps)
tt-cli    ─> tt-core, tt-db, tt-llm
tt-server ─> tt-cli, tt-core, tt-db, tt-llm
tt-watcher─> tt-cli, tt-core, tt-db
```

`tt-server` and `tt-watcher` are separate binaries so the main `tt` stays lean and musl-static: `tt-server` would otherwise drag tokio/axum + embedded web assets into every `tt` invocation, and `tt-watcher` needs glibc (cctk → libxkbcommon).

## Daemon (`tt-serve`, crate `tt-server`)

Async tokio/axum process. `LoopRuntime::run` spawns four independent loops (supervised by a `JoinSet`); each opens a fresh DB connection per unit of work (see Anti-Patterns):

| Loop | Cadence | Job |
|------|---------|-----|
| ingest | ~30s | Scan Claude/OpenCode sessions into the DB, **incrementally** — only sessions touched since `meta.session_scan_cursor`; arm classification if anything imported |
| sync | ~60s | Pull events from remote machines; per-remote `SyncBackoff` on failure |
| classify | 5s debounce, then back-to-back while draining | Auto-classify unassigned activity via `tt-llm` (only runs when a classifier is configured) |
| db_version | 2s | Poll `meta.db_version`; on change recompute the status verdict and push an SSE event |

HTTP (localhost only, `router` in `api.rs`): `GET /api/status` → priority-drift `Verdict` JSON; `GET /api/sse` → live event stream; every other path falls back to the embedded SPA (`web/dist/` via `rust-embed`). systemd unit: `config/tt-serve.service` (`ExecStart=%h/.local/bin/tt-serve`).

The classifier is optional: a missing API key disables the classify loop and records `ClassifierHealthState::Unconfigured`; runtime failures record health + back off. Classifier problems degrade loudly but never crash the daemon.

The classify loop **drains**: a pass is bounded at 200 sessions, so when one finishes it asks whether to run again rather than waiting for the next import. Triggers alone left any backlog bigger than one pass structurally unreachable — the daemon kept pace with new work and never caught up on old, which is how 1.7M events stayed unattributed while `classified_sessions` sat still. The re-arm is decided by `should_drain` in `tt-server/src/loops/classifier.rs` and is deliberately *narrow*: it compares the candidate set (`unclassified_user_sessions`) from before the pass with the one after, and continues only when **both** hold — some candidate the pass looked at is gone, and candidates remain. Re-arming on remaining work alone would repeat a pass whose every verdict is refused, since those candidates survive every pass and each repetition costs another 200 model calls. The pass's own tallies cannot stand in for the comparison: `assigned` counts events, includes window-focus runs the watcher keeps supplying, and so can report progress on every run while every session it touched was refused. A failed pass never drains — `classifier_retry_delay` governs it instead.

## Code Conventions

### Error Handling

- **Library crates** (`tt-core`, `tt-db`, `tt-llm`): `thiserror` typed errors
- **CLI + daemon** (`tt-cli`, `tt-server`): `anyhow` with `.context("message")`

### Lint Suppressions

Use `#[expect(clippy::lint_name, reason = "...")]` — never bare `#[allow]`. Every suppression needs a reason string.

### Workspace Lints (Cargo.toml + clippy.toml)

- `unsafe_code = "deny"` — no unsafe anywhere
- `clippy::all`, `pedantic`, `nursery` = warn
- Allowed: `module_name_repetitions`, `must_use_candidate`, `missing_errors_doc`, `missing_panics_doc`
- `clippy.toml` `disallowed-methods` blocks `tt_core::allocation::allocate_time` → callers must use `tt_db::allocate_for_period`

### Async

`tt-cli`, `tt-core`, `tt-db` are sync (rusqlite is sync). `tt-llm` exposes a **sync** `Classifier` trait; `RigClassifier` drives async `rig-core` on an internal `tokio::runtime::Runtime` (`block_on`), so callers stay sync. `tt-server` is the async crate: `#[tokio::main]` + axum + tokio loops, and it runs every blocking DB/CLI call inside `spawn_blocking`.

### Logging

`tracing` with structured fields: `tracing::info!(count = events.len(), "processed")`. CLI `--verbose` flag sets `debug` level.

### Testing Patterns

- **Unit tests**: `#[cfg(test)] mod tests` at bottom of same file
- **Snapshots**: `insta::assert_snapshot!` for CLI output (report, streams, status, proposals, priority, machines)
- **DB tests**: `Database::open_in_memory()` — no filesystem needed
- **Classifier tests**: `tt_llm::MockClassifier` — scripted `classify` / `describe_stream` results, no network
- **Fixture builders**: `make_event()`, `make_test_stream()`, `TestEvent::tmux_focus()` — small helpers with sensible defaults
- **Integration**: `tt-cli/tests/e2e_flow.rs` spawns actual binary via `Command`
- **Temp dirs**: `tempfile::TempDir` for filesystem isolation

### Configuration

Figment layered loading: compiled defaults → `~/.config/time-tracker/config.toml` → `TT_*` env vars. Keys: `database_path`, `todo_store_path`, `wip_limit`, `drift_window_min`, `ingest_interval_s`, `sync_interval_s`, `[classifier]` (`model`, `confidence_threshold`, `api_key_env`), `[serve]` (`port`).

## Anti-Patterns

- **Additive migrations only**: supported older schema versions migrate forward in `init()`; unsupported versions fail fast (`SchemaVersionMismatch`). See `tt-db/AGENTS.md`.
- **Allocate only through `tt_db::allocate_for_period`** — the raw `tt_core::allocation::allocate_time` is clippy-blocked. Its `end` bound is **exclusive**: an event at exactly `end` belongs to the next period. Intentional test call sites carry `#[expect(clippy::disallowed_methods, reason = ...)]`.
- **Allocation streams the event history and must never materialize it again**: `tt recompute` needs a forward, timestamp-ordered allocation pass, not a `Vec` of every event. Its bounds and integrity warnings are aggregate queries (`event_time_bounds`, `sessions_spanning_multiple_streams`, `sessions_with_tool_use_but_no_start`); the allocation window must go through `for_each_event_in_range` into `tt_core::allocation::Allocator`. Measured 2026-08-10 on the live 2.2 GB corpus (2,738,805 events), the old two-load path took **250.48 s wall, 99% CPU (one of 24 cores), and 8,928,316 KB peak RSS**. Streaming reduced peak RSS to **119,184 KB** and **120,012 KB** in two runs — about **75× less memory**, safely below the plan's 1 GB target — but took **269.72 s** and **270.95 s** at the same 99% CPU: roughly **8% slower than baseline** and **46% slower than the 185.19 s task-1-only run**. This is a memory win, not an unqualified performance win; row-by-row streaming costs CPU the bulk load did not. Parallelizing `union_duration_ms` was measured and **rejected**: the two attempts took **264.34 s / 119,312 KB** and **267.95 s / 119,540 KB**, still at 99% CPU, only **+128 KB** and **+356 KB** of RSS over the first streamed run and with no parallel utilization across 24 cores. The final per-stream union is therefore not where the time goes; the remaining cost is the streaming path itself, not finalization. `allocate_for_period_streams_the_window_instead_of_collecting_it` is a structural guard, not a stopwatch: a test-only per-thread counter makes any call to `get_events_in_range` fail deterministically, and the collecting form was verified to fail that assertion before streaming was restored.
- **`db_version` is the daemon's change signal**: attribution-visible DB mutations bump `meta.db_version` *inside* their own transaction and *only when rows actually changed*; bookkeeping writes (recheck marks, classifier health) deliberately do NOT bump. Break this and the daemon's 2s watcher stops noticing external writes.
- **Daemon DB access**: open a fresh `tt_db::Database` inside each `spawn_blocking` closure and drop it before any `.await`. No `Arc<Mutex<Database>>`, no connection pool — `Database` is `Send` but not `Sync`.
- **`tt sync` must not recompute**: recomputation still walks the *entire* event history — measured at about **270 s of one CPU and 120 MB peak RSS** after streaming — to refresh totals that only `tt streams` reads, and sync pays it once per remote. `tt streams` labels its totals with their age instead. Re-adding `recompute::run` to `sync::run` is a regression — `tt-cli/tests/sync_no_recompute.rs` guards it.
- **A cache nothing refills is not stale, it is wrong, and `streams.first_event_at`/`last_event_at` are that cache**: they hold `MIN`/`MAX` of a stream's event timestamps, and **nothing writes them**. `update_stream_times` — the only stream writer `tt recompute` calls — sets the two time totals, `updated_at` and `needs_recompute`; `tt_core::StreamTime` carries no event timestamps to give it; `mint_stream_in` inserts NULL; `insert_stream` persists what the caller passed, which is `None` at every call site in the tree. The columns are residue of the deleted `--apply` engine: measured live, **985 of 1,245 streams have both NULL, the 260 that do not were all created in 2026-03/04, and their newest value is 2026-04-30 — 99 days behind the newest event**. `tt streams list` filtered its seven-day window on `last_event_at` and therefore printed **"No streams with activity in the last 7 days."** on a database with **90** such streams and 75h of direct time that week. The command was useless as shipped, and it failed *silently and confidently*, which is the same failure mode as the dead watcher above. **The fix is to read `events`, not to make `tt recompute` fill the columns.** Filling them would put the answer back on a cache that goes wrong the instant an event is assigned — and events acquire and lose a `stream_id` constantly, through `assign_events_by_session_id`, `assign_events_by_ids`, `inherit_stream_for_session`, `claim_unassigned_events_for_classified_sessions`, `reassign_session_as_user`, `dissolve_stream`, `release_unattributable_pane_focus` and `merge_streams`. Making the columns real means every one of those maintains the invariant, or the cache is refreshed only by a command that walks the whole event history and that the `tt sync` entry above exists to stop anyone running. `stream_activity_windows` had already made this call for the classifier roster on the same evidence; the inconsistency was one reader trusting the column while another deliberately avoided it. There is no performance case for the cache either: the aggregate costs **0.23s on the live 2.2 GB corpus**. Both readers now go to `events` — `get_streams_for_display` via `stream_activity_windows`, `streams_in_range` via its own aggregate — so no code concludes anything from the columns. They stay in the schema because dropping a column is a table rebuild plus a `SCHEMA_VERSION` bump, and a bump hard-fails every machine's `tt` with `SchemaVersionMismatch` until redeployed, which has already happened here; `Stream` keeps the fields so the row round-trips into the daemon's JSON, carrying a doc comment as the guard against the next reader. Any *new* denormalized column over `events` owes the same question: which write path maintains it, and what does a reader see when none does.
- **Terminal-focus attribution resolves or stays silent**: the `terminal_focus` pass only reads events with `stream_id IS NULL` and only writes a *strict* plurality winner. Never widen `TERMINAL_CORRELATION_WINDOW_MS` to raise coverage (it is measured — see `attribution.rs`), never break a tie, and never route the remainder into a catch-all. An unresolved focus event stays unassigned, where it registers as classification lag; inventing a container for it (`other: shell / nav / transitional`) is the exact failure this pass exists to undo. `assignment_source = 'user'` is never touched. Because the pass reads only unassigned events, focus already swallowed by an invented container is invisible to it until `tt streams dissolve` hands it back.
- **Non-terminal focus binds an artifact, never a moment**: a browser is not a view of the machine's current activity the way a terminal is, so the terminal pass's temporal correlation must not be extended to it. That is measured, not assumed — against artifact-bound ground truth, repo-scoped temporal plurality on a PR page agreed **53.7%** of the time, and its errors are plausible neighbours (`time-tracker: tooling` in place of `time-tracker: tt fixes + todo CLI`), which is exactly the "adopt whatever was nearby" failure. The `artifact_reference` pass instead reads a *durable identity* out of the title — a specific GitHub PR or issue — and takes the stream from the classified session that referenced that same artifact by URL or `#number`. A repository is never enough on its own: `agent-c` spans **224 streams**, so `Work · Pull requests`, `Pull requests · owner/repo`, and `New Tab - Brave` all resolve to nothing. Prose matching is the forbidden surface→stream rule in disguise and was measured twice and thrown away both times (token containment bound `Amazon.com Shopping Cart` to `agent-c: calendar reskins`; exact-subject matching only "worked" at a hand-picked length threshold). **Slack is genuinely unattributable**: `Threads - Trajectory Labs - Slack` names the workspace, not the initiative, and tt cannot read thread content — leave it unassigned. Coverage is deliberately small (20 of 523 artifacts bind, because `agent_sessions` persists only 5 prompts × 2,000 bytes); do not widen any rule to raise it.
- **Falling direct-time coverage is the correct removal of false precision, not a regression to fix**: when this was first written `tt report` showed the week of 2026-07-13 at **4% unassigned direct time** against a then-current week at **48%**, and the obvious reading — that attribution got worse — is wrong and dangerous, because the obvious fix is re-adding cwd inference. **Every percentage in this entry is a dated measurement, not a target, and all of them move**: unassigned falls as the classifier drains a backlog and rises the moment invented attribution is released, so re-measure before concluding anything from a difference. As of 2026-08-08, after the pane release described at the end of this entry, the same two weeks read **33.5%** (24h 53m of 74h 20m) and **61.9%** (47h 26m of 76h 41m) — both higher than the figures above, and both *more* truthful for it. Measured on the two weeks, the drop is entirely one population. In the Jul-13 week, focus events carried 9,145 `inferred` assignments, and they split cleanly by type: **5,988 `window_focus`, none of which has a `cwd` at all**, and **3,157 `tmux_pane_focus`, every one of which has one — of which 2,913 (92%) sit on a `cwd` that maps to the very stream they were assigned to**. That is the cwd propagator's signature, and it is the engine this repo deleted for mapping one directory onto as many as 73 streams. The distinction is the whole point. `window_focus` carries a **title**, so a window run has something to read and the classifier can legitimately place it — 1,629 such events are attributed in the current week. `tmux_pane_focus` carries **no title, no app id and no session** (0 of 102,600), so nothing legitimate has ever placed one; the historical coverage on that type was cwd inference and nothing else. So the honest ceiling for direct-time coverage today is *window focus plus whatever sessions supply*, and the **102,746** unassigned tmux panes (as of 2026-08-08, after the pane release below; ~55,500 before it) are work the product genuinely cannot attribute rather than a backlog awaiting a pass. **The larger number is the truthful one at every point in this sequence — 48% over 4% then, 61.9% over 48% now — and a later measurement showing still more unassigned time is not evidence of a defect.** Anyone reading the trend as a defect and reaching for a directory, a title substring, or a temporal plurality to close it would be re-introducing precisely the failure that cost 695,394 events and 38,491 misnamed-stream assignments to undo. The rule in `tt-core`'s AGENTS.md stands: unidentifiable work stays unassigned, where it reads as classification lag, and inventing a container for it is the one thing forbidden outright.
  **One correction, made later and worth carrying here:** the 2,913 propagated panes counted above were read as a deleted engine's residue, and they were not — they were live assignments the cleanup had missed and the report was still counting, because the propagator wrote the classifier's own `assignment_source`. Releasing them takes this week from 4% to **33.5%** unassigned. The entry's conclusion holds and was understated; see "Deleting the propagator did not undo it" below.
- **A pane's process tree is an identity, and it is the only thing a `tmux_pane_focus` event has**: the two rules above attribute `window_focus`, which at least carries a title. A tmux pane carries none — 0 of 102,600 have one, none has a `window_app_id`, and none has a `session_id` — so the window-run classifier has literally nothing to read and `cwd` is banned outright. That left **102,746 of 118,561 unassigned focus events (86.7%)** as of 2026-08-08 — 55,553 of 71,866 (77%) when this was written, the difference being the pane release with no mechanism at all. What a pane does have is the processes running in it, and a tool call the agent spawns carries that agent's session id in its environment. **The coverage this buys was measured at 100% and that figure is withdrawn**: the sampling ran every 5 seconds while the agent was continuously executing commands, including the sampling script itself, so it manufactured the condition it measured. The harness's long-lived process is **not** in the pane's tree (the tree is `-bash` → `uv run --script`); between commands only a transient command shell and a detached `tt-serve` that inherited the variable carried one. **Live steady-state: 0 of 17 pane-focus events stamped over 90 minutes**, because a focus event fires when the user *switches* panes — exactly when no tool call is in flight there. Treat the stamp rate as unmeasured-and-probably-low until someone measures it over ordinary use; do not count on it to stop the backlog growing. `tt ingest pane-focus` therefore walks the focused pane's process tree and stores what it finds on `events.session_id`. **This is not a surface→stream rule and not temporal correlation, because no stream is derived here at all**: the pass writes `session_id` and never `stream_id` or `assignment_source`, and attribution comes entirely from the already-trusted session→stream path — `Database::assign_events_by_session_id` when the session is classified *after* the stamp, and `claim_unassigned_events_for_classified_sessions` when it was classified *before* it. The pane being focused *is* running that session, which is why an identity is permitted where plurality is not — and why adding any judgement of its own here would forfeit exactly that. The **stamping** is still not a pass in `attribute_unassigned_events`: it happens at capture, while the processes still exist. What *claims* the stamp is a pass, and it had to be built separately — see the entry below, because for a while this half shipped without it and attributed nothing. **It is forward-only, and that limit is the point of stating it**: the pairing lives in process memory and nowhere else, so it stops the backlog growing and does **nothing** for the ~102,700 panes already unassigned — do not present it as a fix for those. **Exactly two variables are ever read**, `OPENCODE_SESSION_ID` and `CLAUDE_CODE_SESSION_ID`, matched **by entry name** and never by substring (a real environment holds `MY_OPENCODE_SESSION_ID`, and notes whose value spells one of these names); an agent's environment is full of credentials, so the one value is extracted and every other byte is dropped, never logged and never stored. Widening that list, or keeping any other entry, is a privacy regression in a tracker. **Bounded twice** — 64 environments and 8 generations, against observed trees of 2–8 processes at depth ≤ 5 — because this runs on every pane focus, thousands of times a day; one walk costs 0.62 ms. Children are read from `/proc/<pid>/task/<tid>/children` for **every** thread, not just the main one: the harnesses fork from worker threads, and the main-thread-only read found **0** session ids across every live pane where the all-threads read found the agent. **Every failure degrades silently and completely**: no pane pid (tmux is asked directly), non-Linux, no `/proc`, permission denied, a process exiting mid-walk, an unparseable pid — each records the event exactly as before this existed. `--pane-pid` is typed as text rather than a number for that reason alone: clap must not be able to reject a hook-supplied value and cost a focus event.
- **A stamped session id is worthless until something claims it, and the claim is a propagation rather than a fourth surface rule**: the entry above shipped only its first half and therefore attributed nothing. The classifier claims a session's events *at classification time*, through `assign_unassigned_events_by_session_id`, so an event that acquires that `session_id` **afterwards** — which is every stamped pane, because a pane is stamped when it is focused and its session may have been classified hours earlier — was reached by nothing at all: `attribute_unassigned_events` held only `terminal_focus` and `artifact_reference`, and neither reads `session_id`. Verified live before the fix: a session in state `classified`, **7** focus events carrying its id, **0** attributed. The stamping mechanism was inert. `tt_db::claim_unassigned_events_for_classified_sessions` is the missing half — it gives an unassigned event the stream of the classified session it belongs to — and it makes this the **third** pass, which is the decision the entry below reserves. **It is not the forbidden rule and the difference is not a matter of degree.** The cwd pass *derived* a stream from a surface: a directory is a property of the machine rather than of the work, so the mapping was one the pass invented and 206 of 1,107 cwds legitimately hold several streams (the worst 73). This pass derives nothing. It reads no `cwd`, no window title, no `window_app_id`, and no moment in time; the event carries the session's own id, put there by an identity established at capture, and the classifier has already ruled on that exact session. The only mapping it applies is one the single trusted engine authored *about this very session*, which is the same principle as `inherit_stream_for_session` handing a subagent its parent's stream. It is also deliberately **not** pane-specific: it claims any unassigned event carrying a classified session's id, because filtering to `tmux_pane_focus` would be a surface rule creeping back in and would strand a late `agent_tool_use` row for no reason. It runs **first**, ahead of the two correlation passes, so a certain identity reaches an event before a correlation can — they do not compete today, since `unattributed_terminal_focus_events` reads only `window_focus`, but the order states which wins if they ever do. A junked session propagates its junk stream, and `tt streams dissolve junk` reverses that exactly as it does for the session itself.
- **The single-stream requirement is the opposite of the cwd pass's discredited uniqueness guard, not a copy of it**: both say "assign only when the mapping is unanimous", and that resemblance is why the distinction has to be written down. The cwd guard was evaluated at run time against a *growing* map, so early unanimity was an accident of sparsity that got locked in and propagated, and it grew **more** wrong as the corpus filled — a directory holding many streams is the normal, correct state of a directory. A session's stream set cannot grow that way: a session is one unit of work with one classifier verdict, bounded by its own history, so its assigned events pointing at two streams is not the normal case but a signal that something else reached it — a human correction moved part of it, or another pass claimed a stray event. In exactly that case the database cannot say which stream a late member belongs to, so the session is **skipped whole**: no winner is picked and no tie is broken, the same discipline as `resolve_terminal_focus` returning `None` on a tie, and the events left behind stay unassigned where they read as classification lag. That includes the case where one of the two streams came from a human — `'user'` is deliberately **not** treated as an authoritative override here, because preferring it would be picking a winner, which is the one thing this pass may not do. The stream is read from the session's **own already-assigned events** because `classified_sessions` records only *that* a session was classified, never which stream it landed on. `assignment_source` is `'session_membership'`, hardcoded so this cannot be reused as an inference primitive, and distinct from both neighbours on purpose: `'inferred'` means the classifier judged content and every guard that makes it safe belongs to `tt classify --auto`, so labelling these rows `inferred` would claim a provenance they do not have and hide a second writer from exactly the audit that caught the last one; `'inherited'` is a *subagent* taking its parent's stream, and `inherit_stream_for_session` re-points `inherited` rows when the parent is reclassified, which must never happen to these. Only `stream_id IS NULL` rows are claimed — strictly narrower than skipping `'user'`, so no assignment by anyone is ever overwritten — and `db_version` bumps inside the pass's own transaction and only when rows changed. **What this does not fix**: the pane half remains forward-only, because the pane→session pairing lives in process memory and nowhere else, so this claims stamps as they arrive and does **nothing** for the ~102,700 panes already unassigned. It repairs a mechanism that was producing zero; it does not clear that backlog, and must not be presented as doing so.
- **Dissolution releases attribution; it never destroys history**: `tt streams dissolve` nulls `stream_id` *and* `assignment_source` so a released event is indistinguishable from one that was never classified — anything less and the next pass skips it. Two invariants are absolute: no event row is ever deleted, and `assignment_source = 'user'` is never released. A stream still holding a human assignment is therefore left standing, because only a human can speak for that content. Which streams deserve dissolving is a per-invocation judgement, so the command takes references and hardcodes no list of its own.
- **Merging moves a human's assignment; dissolving never releases it**: the two commands answer different questions, so they treat `assignment_source = 'user'` in opposite ways, and neither is negotiable. Dissolution says *this was never work*, which contradicts the human, so it leaves those events alone. `tt streams merge` says *this was work, on a different row* — it corrects only which stream holds it, so re-pointing a human-assigned event preserves that verdict and skipping it would strand the human's judgement on a row about to be retired. The shared invariants still hold: no event row is ever deleted, all sources move in one transaction, `meta.db_version` bumps only when rows changed, and tags arrive via `INSERT OR IGNORE` so a tag the target already carries is not duplicated. A merge does *not* refresh `streams.time_direct_ms` — only `tt recompute` writes those — so it marks the target `needs_recompute` and leaves `updated_at` alone, because `tt streams` renders that column as "times last computed" and a merge invalidates those times rather than refreshing them. Which streams belong together is a per-invocation human judgement, so `merge` and `rename` take references and hardcode no list of their own — the ~51 date-suffixed streams are **real initiatives**, repaired by renaming then merging, and a bulk dissolution of them would destroy ~25k correct assignments.
- **Retiring a stream strands references held outside the database, and the reader degrades rather than aborts**: `events.stream_id` is a foreign key, so the DB keeps itself consistent when `tt streams dissolve` or `tt streams merge` removes a row. Nothing protects the references kept *elsewhere*, and each one has now broken in production. **Pending proposals**: `proposals.proposed_stream_id` has no foreign key, so a dissolved stream leaves rows nobody can accept, which once exiled their sessions from later passes and would now suppress a fresh proposal for them; `PROPOSAL_IS_ANSWERABLE_SQL` is what keeps them from doing either (see the proposals entries below). **Priority links**: `~/.local/share/time-tracker/streams.md` maps streams to priorities by slug or exact name, is hand-edited, and is not a database at all — two lines naming dissolved streams (`meetings-coord`, `team-coordination`) made `compute_drift` return `UnresolvedStream`, which aborted `compute_verdict`, which returned **HTTP 500 from `/api/status`** and killed `tt status` and the whole dashboard rail. One stale line in a text file took down the product's main panel. The rule both fixes share: **the reader skips the dangling reference and reports it; it never aborts, and it never edits the user's record to suit itself.** `validate_links` drops such a link and contributes no time for it — a link resolving to no stream owns no time, and inventing a zero-time entry would make an absent stream look like an idle one — then collects it in `DriftReport.dangling_stream_links`. **The report carries it as data and never logs it**: `tt todo drift --json` writes its report to stdout and this process logs to stdout too, so a `warn!` inside `compute_drift` corrupts that JSON. Each caller surfaces it on its own channel instead — one-shot CLI callers (`tt status`, `tt todo drift`) warn on every invocation, while the daemon warns only when the set of dangling links changes (via `should_announce_dangling_links` in `tt-cli/src/drift.rs`). This split prevents the daemon from logging the same stale links repeatedly; measured on the live daemon, the unchanged-set case was **92% of all log lines** (~one every 9 seconds), burying real defects. The daemon tracks the previous set and announces only when it differs, including the first time it sees a non-empty set and when it becomes empty again. A genuinely NEW dangling link still appears at WARN level in the daemon, so new stale links are visible immediately. Deleting the line would be the reader rewriting the human's mapping to spare itself an error — only the user decides a line is stale. The push half is `tt streams dissolve`, which names every `streams.md` link it breaks, in `--dry-run` too because that is where the operator decides, and still removes nothing. Any *new* store of stream ids outside the `events`/`streams` foreign key owes both halves: a reader that degrades and names the dangle, and a warning from the command that creates it.
- **Exactly one inference engine, and the correction surface is not a second one**: `tt classify --auto` is the only path that decides, by machine, which stream work belongs to. Everything that makes that safe is a property of *that* path — recency-ordered bounded selection, subagent inheritance, structural-junk routing, injection filtering, budgeted session fetch, `is_misnamed_stream`, and `stream_exists` validation of a returned id. None of those live in the database, so any *second* writer of `assignment_source = 'inferred'` gets none of them for free. That is not hypothetical: a command that applied an agent-authored JSON blob of assignments produced **68 misnamed streams over 55,031 events and 155h of direct time** — weekly buckets (`workorder-5: IPI envs + wo-005 (Jun14-20)`), catch-alls (`agent-c: misc`), a fresh container minted every week because nothing made the agent reuse last week's. Its ontology rules were prose in a skill file, and prose is not a guard. Deleting it is why `Database::assign_events_by_pattern` and `assign_events_by_time_range` are gone too: both hardcoded `'inferred'` in SQL and existed only to serve it, so removing the primitives makes cwd-pattern and time-range bulk inference a thing you must deliberately re-add rather than merely call. `clear_inferred_assignments` went the same way and for the same reason from the other direction: it bulk-nulled `assignment_source IN ('inferred','todo_link')` in one unguarded statement, had no command behind it and no caller outside its own test, and would also have released `todo_link` — a human's own stream→session mapping, not an inference. Bulk *release* needs the same deliberateness as bulk inference, and `tt streams dissolve` is the guarded surface that provides it. **Human correction is the exception, and stays narrow to earn it**: `tt streams assign` moves only sessions and events named on the command line, never creates the target stream, and writes `'user'` — a verdict every machine writer refuses to overwrite, which is exactly why it must never acquire a pattern, time-range, or file-input form. A bulk surface that writes `'user'` would be strictly worse than the one removed, because the classifier could not repair it afterwards.
- **A link nothing can write is a link nobody has, and `tt todo stream` is the missing writer**: alignment reads todo → stream → priority, and the priority half was healthy — `streams.md` held 25 links, all resolving, none dangling — while the todo half sat at **5 of 166 todos (3%)**, 49 of the unlinked ones still open. So `/api/status` returned `aligned: null` and `tt status` printed `(top todo has no stream link)` permanently: the panel that answers *am I working on the right thing* was inert, and had been for as long as it existed. **That was a missing surface, not user laziness.** `tt todo add --stream` sets the field on a todo that does not exist yet, and `tt todo link` only *applies* a stream the todo already names to an agent session, so changing it on an existing todo meant hand-editing `todos.md` or deleting and re-adding the todo. `tt todo stream <todo-id> <stream-ref>` sets it; `--clear` removes it. Clearing is a **flag rather than a sentinel** because `resolve_stream` matches by exact display name, so any word reserved to mean *no stream* is a name some stream may legitimately hold — and a flag is the half that appears in `--help`.
- **It resolves like the rest of the CLI, stores what readers actually resolve, and infers nothing**: the reference may be an id, a slug, or an exact name (`Database::resolve_stream`), so the user can paste whatever is in front of him — but `todo.stream` is read as a **slug** by everything downstream (`drift::resolved_top_stream_id` and `todo/stream_links.rs` both call `get_stream_by_slug`), so the resolved stream's *slug* is what lands in the file. A stream carrying none is refused, pointing at `tt streams slug`, rather than being given one, and a reference matching nothing is reported with the string that was passed and **never minted** — the same discipline as `tt todo link`. Which stream a todo serves is the human's to name: deriving it from the todo's text, priorities or sessions would be a second inference engine, and there is no bulk form for the reason `tt streams assign` has none. **The edit is one field of one line.** The stream is resolved *before* the store is loaded, so an unresolvable reference or an unknown id leaves the file byte-identical; text, id, priorities, `when`/`due`/`pin`/`quick`, sessions, line position and every other line of the user's hand-maintained record survive untouched. `todos.md` is the user's own record, exactly as `streams.md` is — a writer he invoked on one named todo may change exactly what he named, and nothing else.
- **A dead input must announce itself, and failing closed is not the same as failing quietly**: the entries above are about a reference the reader can no longer resolve. This is the harder case — nothing is unresolvable, every number still computes, and the computation is simply missing an input. `tt-watcher` emits `window_focus` and `afk_change`, the only capture of non-terminal attention there is, and the copy distributed via mise was built when `SCHEMA_VERSION` was 10. The schema is now 12, so it died at startup on `schema version mismatch: database has version 12, expected 10` and **systemd restarted it 35,051 times**. Both event types stopped at **2026-07-29T05:01:20Z** and produced nothing for **nine days**, while `tmux_pane_focus` — a different mechanism, the tmux hook — kept flowing at 600–1900/day. So every hour of browser, Slack, meeting and GUI attention was invisible to direct time, AFK detection never ran, and `tt status` and the dashboard reported confident numbers and **said nothing**. Nobody noticed until someone read `systemctl status` by hand. **The watcher's fail-closed behaviour is correct and must not change**: the additive-migration rule in `crates/tt-db/AGENTS.md` exists because a binary that guesses at an unknown schema writes corrupt attribution, and corrupt direct time is worse than absent direct time. Refusing to start was the watcher doing its job. The defect is entirely on the reading side — the product could not tell its user that one of its own inputs was dead — so the fix is a report, never a relaxation of that check.
- **The classifier is an input too, and `tt status` called it healthy while it was off**: `classifier_status` read `consecutive_failures` and `last_success_at` and never `ClassifierHealthState`. An unconfigured classifier does not *fail* — it never runs — so failures stay 0 and `last_success_at` keeps whatever the last configured run left behind, which falls straight through to `classifier ok · last run 30m ago` while nothing is being classified at all. Reproduced here by accident and then on purpose: a daemon restarted without `ANTHROPIC_API_KEY` sat `unconfigured` for an hour, `classified_sessions` did not move, and `tt status` reported the classifier healthy throughout — the outage was found only by reading `meta` directly. That is the dead-watcher failure in a second input, and it is worse here, because this input is the only thing that attributes work to a stream. The state is now checked **first**, before the failure count, since an unconfigured classifier has nothing to count. `config/tt-serve.service` shipped with no key provision at all, so every install landed in exactly this state; it now wraps `ExecStart` in `secrets ANTHROPIC_API_KEY -- ` so the value reaches the child's environment without touching disk, a log or the unit file. The key is agent-tier, so it resolves with no tty and no human touch — verified under `systemd-run --user` before the unit was changed, since a wrapper that needs a terminal would turn a silent outage into a daemon that will not start. A machine without secretsd drops the wrapper and supplies the key another way; the commented `EnvironmentFile` line in the unit names one. The status line remains the backstop, because a unit is only correct until someone starts the daemon by hand.
- **The distribution channel is a single point of failure, and it had already taken the CLI down without anyone noticing**: `tt` and `tt-watcher` are both provisioned by mise from `github:sjawhar/time-tracker`, so both resolve to the newest **release**. The newest release is v0.7.0 (2026-07-20), built when `SCHEMA_VERSION` was 10. That is the documented cause of the nine-day watcher outage, and the same binary is what `tt` on `PATH` resolves to — `/home/sami/.mise/installs/tt/latest/tt`, ahead of `~/.local/bin` and `~/.dotfiles/bin`, both of which carry current builds. So **every interactive `tt` command failed outright**: `Error: failed to open database — schema version mismatch: database has version 13, expected 10`. `tt report`, `tt status`, `tt streams`, `tt proposals`: all dead, for as long as the schema had been past 10. It went unnoticed for the same reason the watcher did — development runs `./target/release/tt`, which is never the binary the user runs. **Check `command -v tt`, not the build you just made**, before concluding any CLI-facing change works. The fail-closed schema check is correct and must not be relaxed (`crates/tt-db/AGENTS.md` says why); the defect is that a release was never cut. Both mise binaries have been overwritten with current builds as a stopgap, and a `mise install` will silently restore the broken ones — which is why the `tt-watcher` systemd drop-in stays in place, since it points at `~/.local/bin` where mise cannot reach. The real fix is a release carrying `SCHEMA_VERSION >= 13`, and it must carry the `sqlite_master` probe in the v≤12 migration arm or it bricks every capture-only machine.
- **`set-hook` does not error on a hook name tmux does not know, so two of the five capture hooks never fired**: `config/tmux-hook.conf` used `pane-focus-in` and `pane-mode-changed`, and **neither is a hook name tmux 3.7b knows**. tmux accepts the `set-hook` silently, the name never appears in `tmux show-hooks -g`, and nothing ever runs — which is indistinguishable from a working hook until you go looking for the events it should have produced. The evidence was there the whole time: **`tmux_scroll` had 0 events in a 2.7M-event corpus**. That is not a cosmetic loss, because `allocation.rs` treats `TmuxScroll` as confirming focus and resetting the attention window, so scrolling back through terminal output — reading, which is attention — never extended a window, and long reads silently fell off the five-minute cap. The supported equivalents are `after-copy-mode` (verified by probe that it fires) and `client-focus-in`. **Verify a hook by the events it produces, never by the absence of an error**, and re-source with the tt hooks cleared first: every line uses `-ga`, so a second source appends a duplicate and double-writes every focus event. **This file passes no `--pane-pid`, and that is deliberate**: a hook config reaches a machine independently of the binary, and a `tt` that predates the flag exits non-zero on it — not a degraded optimisation but total capture loss. Deploying a config carrying it to a host running an older `tt` killed every pane-focus event there for two and a half hours, silently, with the only trace in `hook.log`. `pane_session.rs` asks tmux for the pid when it is absent, so omitting it costs one round trip and removes the version coupling. `scripts/deploy-remote.sh` installs the binary before the config for the same reason. The installed hooks had also drifted from this file and passed no `--pane-pid`, which still worked only because `pane_session.rs` falls back to asking tmux for the pid.
- **Staleness is only answerable per machine, and expectation is derived, never declared**: `tt_db::last_local_event_per_type` groups `events` by type over the rows this machine produced, and "this machine" comes from the data rather than from `machine.json` — the `machines` table is populated only by `tt sync` registering a *remote*, so an event whose `machine_id` is absent from it (the NULL rows written before `tt init` included) was produced here. Reading the identity file instead would put this query's answer outside the database and out of reach of an in-memory test. Per-machine scoping is not tidiness: the existing `Sources:` block in `tt status` groups by the `source` string across every machine, so a synced remote's healthy watcher reports under the same `local.cosmic` source and makes the type look alive. That is reproducible in one command — inject a nine-day-old local `window_focus` plus a fresh remote one and `Sources:` prints `local.cosmic` as current while the local watcher is nine days dead. **Absence is not staleness**: a type appears in the result only once this machine has produced one, so a server or a fresh install that never ran a watcher has no expectation to fall behind and is never flagged. That is why `stale_event_sources` filters the *observed* set by `MONITORED_LOCAL_SOURCES` rather than walking the monitored list and calling a missing type broken — the inverted version would make every headless box cry wolf forever. The monitored list is a table naming each type's emitter, so adding a source is one line and the threshold, the CLI line and the daemon's change detection all pick it up; naming the watcher's two types explicitly beats monitoring everything, which would flag `browser_tab` (an unimplemented input with zero events) and every agent type the moment a quiet week passed.
- **`STALE_LOCAL_SOURCE_HOURS` is 72, and the number is set by the longest *healthy* silence, not by taste**: the watcher emits on window changes and AFK transitions, so a machine nobody touches emits nothing — silence means *away* before it means *dead*. A night is ~10h; the long legitimate case is a weekend, and stopping Friday 18:00 to resume Monday 09:00 is **63 hours** of correct quiet, which rules out 24h and 48h outright. 72h clears that by 9 hours and would have caught this incident on **day 3 of 9**. It is deliberately a constant and not a config key, exactly like `DARK_AFTER_DAYS`: this is a "something is broken" alarm, not a preference worth tuning away. The asymmetry is what justifies erring short — a false positive costs one line of status output saying, truthfully, that nothing has arrived in three days, while the false negative cost nine days of direct time that silently did not exist. A four-day holiday weekend will therefore say so once; that is the right trade and not a reason to widen this to a week, at which point this incident would have surfaced on day 7 of 9.
- **The same two-channel split as dangling links, for the same measured reason**: `compute_verdict` computes `stale_event_sources` and logs nothing, and `compute_drift` stays untouched — `tt todo drift --json` writes its report to stdout and this process logs to stdout too, so a `warn!` in that path corrupts the JSON. Each caller announces on its own channel. One-shot CLI (`tt status`) warns on every invocation and **also renders a line in the human block**, above `Sources:`, because a dead input is precisely what a human running `tt status` needs told and the JSON alone reaches only the dashboard. The daemon announces only when the set *changes*, via `should_announce_stale_sources`; both helpers now delegate to one `warning_set_changed`, since the split they implement is one rule rather than two. Stale sources compare as whole entries, `last_seen` included, which is what the daemon wants: a silent source's `last_seen` is frozen by definition, so it moves only when the source came back and stopped again — worth saying out loud. Verified against a real daemon on a scratch DB: two announcements on first detection, **still two** after three subsequent `db_version` recomputes with an unchanged set, and a third the moment `window_focus` recovered and the set shrank to `afk_change` alone.
- **The current-stream rail reads the newest *attributable* focus event, not the newest focus event**: `drift::current_stream` answers "what am I working on right now", and it took the single newest focus row and returned `None` if that one carried no stream. That was fine while cwd inference gave every `tmux_pane_focus` a stream, and it broke the moment the release described below returned 47,082 of them to unassigned. Panes now fire *more often* than window focus (1,135 against 703 in 24h) and **8 of those 1,135 carry a stream against 450 of 703 window-focus rows**, so the newest focus event is almost always an unattributable pane and the rail went blank while perfectly good attribution sat seconds behind it. Measured over 24h at 290 five-minute probes, 176 of which had focus activity: the old rule showed a stream on **40**, the new one on **95** — the panel a user watches all day was blank 77% of the time it had something to say. **This is not the forbidden surface→stream rule and it is not temporal correlation**: no stream is derived here at all, the rail simply skips rows that name *no* stream to reach the newest row the trusted engine already assigned, and the `attention_window_ms` bound still applies to *that* row, so staleness stays capped at five minutes. When nothing in the window resolves it still reports nothing — unattributable focus is left unassigned rather than given a container, exactly as everywhere else. The run's `since` walk-back skips a blank row rather than breaking on it, for the same reason: absence of evidence is not evidence of a *different* stream, and breaking would truncate nearly every run to nothing given how the two types interleave. A row naming a genuinely different stream still ends the run.
- **A QA tool that captures a spinner is worse than one that fails, because the artifact looks like evidence**: `scripts/dashboard-screenshots.sh` is the documented visual-QA path, and it could not have worked. Four defects, each silent. It passed `screenshot.js` **no URL**, so the tool fell back to its default port and photographed whatever else was listening rather than the server the script had just seeded and started three lines earlier. It wrote to `../../.screenshots/` from `crates/tt-server/web`, which is `crates/.screenshots`, not the repository-root directory `.gitignore` names. It backgrounded the seeded server on the **inherited stdout**, so the caller's pipe stayed open for the life of that process and the script appeared to hang long after finishing — observed as a 45-minute stall with an orphaned `tt-serve --port 4174` still alive. And `set -e` with no `trap` meant any failure leaked that server, holding the port against the next run. All four are fixed, and the script now exits 0 with five captures in `.screenshots/` and no orphan.
- **Wait for content, never for a fixed delay**: the capture waited for the `aside` selector plus one second. The shell renders immediately, so that proves nothing about whether any panel has data — against the real 2.7M-event database it produced a 14 KB image of "Loading..." and "Loading Timeline...", where a real capture is 230 KB. `screenshot.js` now waits for `networkidle`, then polls until no element's text matches `/Loading/i`. Polling the **whole body** rather than the first match is load-bearing: the sidebar and the timeline load independently, so waiting on one matched element returns while the other still spins, which is exactly how the 1080x1920 capture kept its timeline placeholder after the first fix. Both waits fall through on timeout rather than failing the run, because a capture that shows a stuck panel is still evidence — it is the *silent substitution* of a spinner for content that had to go.
- **A folder is not a project, and the pass that assumed it was is gone**: the rule above has now removed two engines, not one. `tt ingest sessions` used to run `auto_assign_events_to_streams`, which built a cwd→stream map (plus a `/home/<user>/` suffix map for cross-machine paths) out of already-assigned events and claimed any unassigned event whose directory mapped to exactly one stream. It was the largest assigner in the database — **695,394 events, more than every other assigner combined**, of which **38,491** landed in streams whose names `is_misnamed_stream` rejects. Its uniqueness guard is what made it look safe, and the guard is the bug: it is evaluated at run time against a snapshot, so a directory that maps to one stream early gets locked in and propagated, and only *later* does the classifier put a second stream in that directory. Measured on the live DB, that has already happened almost everywhere — of 1,107 distinct cwds, 901 map to one stream but 206 map to several and **the worst maps to 73**.
- **Why removing it costs no coverage**: the cwd pass no longer clears a backlog. **878,110 of the 959,652 unassigned events with a cwd (91.5%) are now skipped as ambiguous**, and on the live DB the pass would assign **0** events on its next run — the map it depends on has saturated. What it still does is race the classifier for *freshly ingested* events, where that map is sparse enough to look unanimous, and it wins because ingest runs every ~30s while classification is bounded per pass; it claimed ~4.5k events/day that way, 7,992 on its last full day. That flow is not lost. Of it, **91.5% belongs to sessions `tt classify --auto` reaches** — 70.0% by content classification and 21.1% by subagent inheritance — so the pass was pre-empting a better answer, not supplying a missing one. The remaining 8.5% is `tmux_pane_focus` carrying no session at all, which the classifier never reached even while the pass existed. The primitive went with it: `Database::get_events_without_stream` returned full rows and was the only whole-table scan of unassigned events, so it is now `unassigned_event_ids` and returns ids alone — re-adding any surface→stream sweep means deliberately writing a query that selects the surface, rather than finding the scan already built. The measured exception this does **not** cover is `assign_terminal_focus`, `assign_artifact_focus` and `claim_unassigned_events_for_classified_sessions`, which resolve a remote host, a specific pull request, or the session an event is a member of to work that is already classified, and never claim that a directory is a stream.
- **Deleting the propagator did not undo it, because it signed its work with the classifier's name**: the two entries above describe removing the engine and releasing 777,583 of its assignments. That cleanup was **incomplete, and no audit keyed on `assignment_source` could have noticed**, because the propagator wrote `'inferred'` — the classifier's own value — so its rows and real classifications are indistinguishable by provenance. **Any future question of the form "how much cwd inference is left?" must be answered structurally, never by source.** Measured on the live corpus after that cleanup: **47,089 `tmux_pane_focus` events still carried `'inferred'`**, of which **44,228 (94.0%) sit on a `cwd` that also carries the very stream they were assigned to** on an independently-classified event — the propagator's signature, intact and still counting. `tt streams release-pane-focus` is the undo, and `tt_db::release_unattributable_pane_focus` holds its rule.
- **The selection rule is structural, and the structure is what makes it provable rather than merely likely**: the population is a `tmux_pane_focus` with a NULL `session_id`, and such an event cannot have been legitimately classified by anything in this tree. It exposes no evidence — **0 of 102,748 carry a window title and 0 carry a `window_app_id`** — and, more decisively, no writer can even select it: every session-keyed writer (`assign_events_by_session_id`, `inherit_stream_for_session`, `claim_unassigned_events_for_classified_sessions`, `reassign_session_as_user`, …) filters on `session_id = ?`, which NULL never matches; the only id-keyed machine writer, `assign_unassigned_events_by_ids`, is fed exclusively by `unattributed_terminal_focus_events`, whose query reads `type = 'window_focus'`; and the `terminal_focus` and `artifact_reference` passes are likewise `window_focus`-only. So the rule rests on the shape of the writers, not on a guess about the data. **The cwd-matching heuristic is reported alongside it but not used**: it identifies 44,228 of the 47,081 structural candidates, and the 2,853 it misses are exactly as unattributable as the rest — matching a directory would make the cleanup depend on the very signal the product forbids, to catch 94% of what the structure catches whole.
- **The `session_id` half of that rule is load-bearing against live data, not just in principle**: **7 `tmux_pane_focus` events carry both a session id and `'inferred'`**, dated 2026-08-08, and they are the process-tree stamp working exactly as designed — stamped at capture, then claimed through the already-trusted session→stream path. A rule reading "release every `inferred` tmux pane" would destroy the only mechanism that has ever legitimately attributed one, on the day it started producing. Verified on a copy: after the release those 7 keep their stream, all 9,712 `inferred` `window_focus` rows are untouched, and 0 sessionless panes still hold attribution.
- **Release means both columns, and that is why one extra row is in scope**: `stream_id` and `assignment_source` both go NULL, so a released event is indistinguishable from one never classified — the same semantics as `tt streams dissolve`, and for the same reason: every later pass reads `stream_id IS NULL`. One live row proves the columns must be handled together — a pane carrying `'inferred'` with **no** stream, left by a stream-keyed cleanup, which a rule selecting on `stream_id IS NOT NULL` would leave asserting a provenance it never had. The predicate is therefore "carries either column", which also makes the command idempotent: a second run reports 0 because a released row carries neither. **Nothing is deleted and no stream is retired** — these events were filed under containers that may hold real work too, and judging a stream stays `tt streams dissolve`.
- **The measured impact is that a third of a week's attention was invented, which is the "false precision" entry above being paid rather than contradicted**: applied to a copy of the live database, the week of 2026-07-13 moves from **2h 47m unassigned (3.7%) to 24h 56m (33.5%)** of 74h 20m direct, and the week of 2026-04-20 from **19h 56m (27.6%) to 50h 4m (69.2%)** of 72h 21m. Wall clock, total direct and total delegated are **identical before and after** in both weeks — the events still accrue attention, they simply stop naming a stream — and the top of the report reorders as the containers give back what was never theirs (`dpi` 10h 44m → 6h 53m, `agent-c: WO-005 CI + contract-SSOT` 6h 49m → 2h 58m). Read this with the entry above on falling coverage: that entry already measured **2,913 of 3,157 propagated panes in this exact week** and read them as a deleted engine's residue, when they were live assignments still being counted. Its conclusion was right and understated — 4% was not the truthful number, and neither was the corrected figure it implied.
- **A read command must not write**: the removed blob surface had a matching read half (`tt classify --json`, and a deprecated `tt context` alias) whose job was to dump sessions and event clusters for an agent to reason about — including a `proposed_stream` field derived from a cwd→stream map, i.e. the folder-named-stream failure served as a machine suggestion. Both are gone with it; what remains reads its answers from `tt report`, `tt streams list`, `tt proposals ls`, and `tt status`. The one write those dumps performed, applying a todo's stream slug to that todo's linked sessions, moved to `tt todo link`, where the mapping is actually created. Unassigned activity is not a backlog for a human to sweep: the daemon classifies continuously, and work the classifier refuses to place stays unassigned on purpose, where it registers as classification lag.
- **Classification selection is recency-first, bounded, and spends no call it can avoid**: `unclassified_user_sessions` orders `start_time DESC` and caps each pass, so a session started since the last pass jumps ahead of a backlog measured in thousands — the arbitrary `ORDER BY session_id` it replaced left today's work unreached for the ~65 hours a full pass takes. Three populations never reach the LLM: **subagents**, which take their parent's stream via `inherit_stream_for_session` because a subagent serves its parent's task and has no stream of its own; **subagents whose parent was never indexed**, a bounded 2026-04 ingest defect that is junked rather than given a fallback classification path; and **structurally junk sessions** (`tool_call_count = 0 AND message_count <= 2`). Do not drop that message-count clause — among tool-free sessions with three or more messages, half are real tool-free work (a contract review, a vendor pricing evaluation). Junk is *routed*, never deleted: it lands on the reserved `junk` stream, so `tt streams dissolve junk` reverses a rule that starts eating real work.
- **Focus attribution gets its own budget, and the budget is what protects it — not the order**: `run_auto` has two phases that spend model calls, and only one of them was bounded. `classify_sessions` was capped at `SESSIONS_PER_PASS`; `classify_window_runs` iterated every unassigned run and ran *after* it. That failed in both directions at once. Unbounded, it could emit thousands of calls in one burst — exactly what the other bound exists to prevent. And until it did, its work sat behind the session backlog: at the observed ~1 classification a minute a full pass is ~3.3 hours, and the queue in front was **3,444 sessions**. The window phase is the only path focus events ever reach, because they carry no session — **0 of 29,730 have one** — so nothing else picks them up. Measured consequence: `assignment_source = 'inferred'` on focus events stopped at **2026-08-05T02:16**; 2026-08-06 produced 1,882 focus events and attributed **0**; 2026-08-07 attributed 3 of 847; and over the six hours before the fix, `tmux_pane_focus` attribution ran **0 of 383**. Nine days in which the product's headline number silently stopped being computed and the dashboard's current-stream rail — which reads the latest focus event's stream — stayed blank. **Focus events are direct time**, and this file says direct time is the answer whenever the user asks where his time went and the primary axis of every human-readable view; a phase that produces it must not be the one that queues. So `WINDOW_RUNS_PER_PASS` is a **second, independent bound rather than a shared budget** — neither phase can spend the other's calls, so every pass reaches both — and the window phase runs **before** `classify_sessions`. Ordering is what makes that guarantee unconditional rather than merely budgeted: a pass is hours long, `run_auto` runs inside a `spawn_blocking` the daemon abandons on shutdown, and any hard error aborts the phases behind it, so whichever phase runs last is the one a cut-short pass drops. Delegated time going stale costs context; direct time going stale costs the headline.
- **The phase order was inverted and then put back, on arithmetic rather than principle**: focus-first was introduced so direct time would never queue behind a session backlog, which is the right instinct and the wrong conclusion. With the window phase running first at 400 calls and the observed rate, a pass spent hours there before reaching a session: measured, `classified_sessions` sat unmoved at **2,003 across 25 minutes** while the classifier reported success throughout, the session backlog held at **3,559**, and the events waiting on those sessions *grew* by 87. The two phases are not comparable in yield, which is what settles it. A session classification attributes every event carrying its id — **1,339,657 events across 3,559 sessions, ~376 per call**. The window phase places **~11 focus events a day** against 400 calls a pass, because 0 of 403 pending proposals reach the 0.80 threshold. Focus-first therefore spent whole passes on the phase that attributes almost nothing while starving the one that attributes almost everything. The original concern is still met, by the bound rather than the order: `WINDOW_RUNS_PER_PASS` is an independent budget, so focus cannot be starved of *calls* by a session backlog. What it can lose is a pass cut short at shutdown, and losing ~11 events a day from a near-zero-yield phase is the cheaper failure by four orders of magnitude. `window_focus_is_classified_even_when_the_session_backlog_fills_a_whole_pass` now pins the bound-independence guarantee rather than the order.
- **`WINDOW_RUNS_PER_PASS` is 101, and the 400 it briefly held was sized on the wrong metric**: 400 came from the two backlogs' ratio — ~28,717 runs against ~3,709 sessions — which would be right if a call in each phase bought the same thing. It does not, by four orders of magnitude. A session classification attributes **~376 events per call** (1,339,657 across 3,559 sessions); a window-run call attributes **~0.03**, because the phase places ~11 focus events a day against its whole budget and **0 of 403 pending proposals reach the 0.80 threshold**. A 600-call pass split 200:400 therefore spends two thirds of itself on the phase that attributes almost nothing. Measured live at that split: `classified_sessions` sat at **2,194 for 25 minutes** while the classifier reported success throughout — the session phase had finished its 200 and the pass was grinding through 400 window runs, so sessions advance during only a third of each pass. At 101 they get two thirds, roughly halving the time to clear the session backlog. **Nothing is starved**: the bounds stay independent, so focus attribution receives its own calls every pass regardless of the session backlog, which is what `window_focus_is_classified_even_when_the_session_backlog_fills_a_whole_pass` pins. 101 is the original pace-based sizing — inflow 1.31 events/min at peak against a 3.9/min drain gives `W >= 1.31 × (200 + W) / 3.9`, i.e. `W >= 100.81`. Keeping pace is the most this phase can usefully do while its answers do not clear the bar; the backlog it cannot clear is a question of evidence per run, not calls per pass. The ordering half is unchanged: `build_unassigned_window_runs` yields oldest-first, so `newest_first` reorders before the cap, and a run whose start cannot be read sorts to the tail without warning.
- **The window-run bound is not what limits focus attribution, and raising it did not help**: measured over 24 hours after raising it to 400, **1,834 focus events arrived and ~189 were placed** — 121 by `terminal_focus` (temporal correlation, no model call), 57 as junk, and only **11** by the window-run phase. Of **403 pending proposals across both scopes, none reaches the 0.80 threshold**; the best is 0.78 and window runs average 0.59. A run's payload is a handful of window titles, too thin to answer confidently, so nearly every call ends as a sub-threshold proposal rather than an assignment. The backlog therefore grows by roughly 1,600 events a day and no per-pass bound changes that. **The constraint is evidence per run, not calls per pass** — do not tune this constant again expecting the backlog to move. That `terminal_focus` places 11x more than the classifier, for free, is the shape of the alternative worth pursuing. Four separate short-window measurements of the drain rate (−83 days, −38 days, +0.81/min, net-draining) all disagreed because inflow swings 2x between peak and mean; only the 24-hour figures above are load-bearing.
- **Structurally junk sessions are routed in bulk before selection, because inside the bounded loop they spend the session budget on sessions no model ever sees**: `is_structurally_junk` costs no model call, but it used to be checked only *inside* `classify_sessions`' loop, so a junk session still occupied one of `SESSIONS_PER_PASS`'s 200 slots. Measured live over ten minutes with 9,255 junk and 3,244 real candidates queued, junk cleared at **13.2/min** (instant — no model call) against **1.4/min** for real candidates, a ~9:1 ratio matching the pass summary's `junked=136` of ~200 slots; a later hour on a fuller backlog read **840 junk sessions classified against 20 real ones**, with summaries at `junked=171..177`. So roughly two thirds to nine tenths of every pass's session budget went to sessions the model never saw, and the concurrency added to `classify_sessions` could not help — only ~29 real sessions per pass ever reached a model, and eight concurrent calls cannot speed up calls that are never made. `tt_db::route_structurally_junk_sessions` now settles them ahead of every phase in `run_auto`, bounded by `JUNK_ROUTING_PER_PASS` (5,000). **That bound is a latency ceiling on one write transaction, not a budget** — routing spends no model call and is three `UPDATE`s against indexed columns, so the only thing it must not do is hold a transaction open long enough to stall the ingest and sync loops. Sizing it near `SESSIONS_PER_PASS` would reproduce the starvation one layer down.
- **Routing is what removes junk from the candidate set; filtering it out of the selection query is still forbidden**: the bulk step *answers* a junk session — its events gain the junk stream, so the `EXISTS (… stream_id IS NULL)` clause `unclassified_user_sessions` reads stops matching it. Excluding it from that query instead would mean it is never routed and accumulates forever, which is why the query is unchanged. Four properties hold the step together. Junk is **routed, never deleted**, so `tt streams dissolve junk` reverses it exactly as it reverses the per-session path, and only `stream_id IS NULL` rows are claimed — strictly narrower than skipping `assignment_source = 'user'`, so no assignment by anyone is overwritten. **Subagents inherit the junk stream here too**: a parent's zero tool calls do not make that unreachable, because `agent_sessions.parent_session_id` is written by ingest rather than derived from a tool count, and `subagents_of_a_junked_session_inherit_the_junk_stream` is a live test of exactly that shape. **The per-session check inside `classify_sessions` stays** as the correctness backstop, for a session that becomes junk between the bulk step and selection. And the SQL predicate in `structurally_junk_sessions` is a bounded pre-filter rather than a second rule: the caller re-checks every row against `tt_core::is_structurally_junk` itself, so the two cannot drift into disagreeing about what junk is. Both counters move — sessions into `junked`, events into `assigned` — because the per-session path moves both and a summary that folded in only the first would understate the pass by exactly the work this step took over.
- **A short measurement of this drain rate is worthless, and that has not changed**: the rate depends entirely on the junk:real mix at the recency-ordered head, which is why successive samples read 1.4, 2.0 and 5.2 sessions/min on one backlog. **Do not raise `SESSIONS_PER_PASS` on seeing a slow drain.** With junk settled ahead of selection the whole 200 now goes to candidates a model can actually answer, so a pass that still looks slow is reporting the model's own rate — measured at roughly 3.9 classifications a minute when healthy — and raising the bound classifies nothing faster.
- **Giving a window run temporal evidence was built, measured, and removed — it raised confidence and placed nothing, and the gain landed in the wrong place**: the entry above says the constraint is evidence per run, so the next thing to try looks obvious: tell the model what work was demonstrably going on around the run. **It is not in the tree. Do not re-add it on intuition — this is the record of it having been tried properly.** What existed briefly: a `tt_core::attribution::streams_active_near` tallying the classified `tmux_pane_focus` / `agent_tool_use` / `user_message` rows within ±120s of a run's span and returning *every* stream with its share and no winner, a batch load per pass in `classify_auto`, and a prompt block rendering the busiest 8 as `id  name  N events` with wording telling the model it decided nothing. The design was sound on the constitutional question — a tally with no winner cannot become an assignment by itself — and it still failed on the numbers. It was A/B'd rather than watched: **45 real unassigned window runs** from a read-only snapshot of the live database, sampled stride-8 across the newest 400 runs (the exact population a pass reaches, spanning 12 days), each classified **twice** — once with the shipped payload, once enriched — interleaved per run so provider drift hits both arms alike, against the production `claude-haiku-4-5`, the production `RigClassifier` with session fetch attached, and the production 1,201-stream roster. 90 calls, 0 errors, 599s.

  | arm | mean | median | max | **≥ 0.80** | assignable (≥ 0.80 **and** names a stream) |
  |------|------|--------|-----|-----------|------------------------------------------|
  | shipped payload | 0.243 | 0.20 | 0.82 | **1 / 45** | **1 / 45** |
  | enriched | 0.343 | 0.35 | 0.85 | **1 / 45** | **1 / 45** |

  The confidence shift is real, consistent and useless. On the 41 runs that had any evidence the mean rose **+0.110** and 30 of 41 went up, and the mass moved out of the bottom bucket (`<0.20`: 21 → 12) into the band just under the bar (`0.60–0.79`: 2 → 8). **Not one additional run crossed 0.80.** The single crossing is the same run in both arms. Enrichment moves the distribution and stops short of the threshold, so it converts sub-threshold proposals into slightly-less-sub-threshold proposals — which is what the previous entry already said more calls do.

  **The gain is concentrated on exactly the titles that cannot name work, which makes it a hazard rather than a partial win.** Split by title class against the taxonomy in `tt-core`'s `AGENTS.md`: the population it says *can* name work gained **+0.058** (n=12), the population it says *cannot* gained **+0.115** (n=33). `terminal` — the cleanest attributable class, and the one `terminal_focus` already places for free — gained **+0.000** (n=7). The individual movements are the argument: `Meet - ryz-jirp-qzv - Brave`, a Google Meet **room code**, went 0.35 → **0.75** and named an *existing* stream; `Sign in - Google Accounts - Brave`, an auth flow, went 0.15 → **0.65**; `New Tab - Brave` went 0.35 → **0.60**. Those titles identify no work at all, and the evidence made the model more willing to adopt whichever stream happened to be busy — the same "adopt whatever was nearby" failure measured at **53.7%** agreement and rejected twice already, surfacing this time as confidence inflation instead of as a bad assignment. **Only the 0.80 threshold stopped it becoming one, which is the strongest argument on file for not lowering that threshold and for never special-casing it per scope.** Do not read the +0.110 as progress toward a working mechanism; read the 0.75 on a meeting room code as what the +0.110 is made of.

  So this was a **negative result, and the constraint named above survives it**: a run's problem is not that the model lacks context about the moment, it is that a window title on Slack, a mail inbox, a Meet room or a blank tab does not name an initiative, and no amount of surrounding context makes it. It was reverted rather than left switched off, because dead code invites being switched on. Do not retry it by widening the window (±120s was already the measured knee — coverage 82% / 84% / **89%** / 90% / 90% at ±30 / 60 / 120 / 240 / 480s against a busiest-stream share of 0.594 / 0.563 / **0.543** / 0.471 / 0.391, so wider is *less* concentrated for no coverage), by showing more than the busiest handful of streams (the top 8 already carried 99% of the activity), or by adding a second evidence channel of the same kind. **`terminal_focus` placing 11x more than this phase, for free, remains the shape of the alternative worth pursuing** — it resolves a remote host to work that is already classified, rather than asking a model to interpret a title that names none.
- **The drain probe stays session-only, and that is the safe direction**: `should_drain` compares `unclassified_user_sessions` before and after a pass, and bounding the window phase does not change what it reads or what it means — the session phase still selects the same 200 candidates from the same query, and a `window_focus` row carries no `session_id` so it can never enter that set. What *is* new is that window runs can now outlive a pass, and the probe cannot see them. That errs safely: an unseen leftover makes the loop wait for the next trigger rather than spin, which is the failure `should_drain` exists to rule out. It is also mostly moot, because focus inflow arms classification on its own — the tmux hook's events reach the DB through `import_local_events`, so `ingest_once` returns `imported > 0` and re-arms every ~30s. Do not grow the probe a window-run half to close the remaining gap: it would load every unassigned `window_focus` row twice per pass to answer a question ingest already answers, and a run's identity is its event-id set, which changes as its events are assigned, so the set-difference the probe depends on would not mean the same thing on both sides.
- **Never invent a container, and reject the shape rather than the substring**: a classifier answer naming an activity (`other: shell / nav / transitional`), a date (`misc (Jun14-20)`, `infra: devbox-mx recovery (Jun6)`), or a leftover (`misc: stragglers`) is refused by `tt_core::is_misnamed_stream` and the candidate is left unassigned, where it registers as classification lag. New-stream creation stays enabled — the guard is the name, never a ban on output. A name fails only when **every** token is generic, so one subject token rescues it: `agent-c: calendar navigation debugging` and `misc: webcam troubleshooting` are real work and must keep passing. A `%nav%` substring rule written during remediation matched the first of those. A lone day buckets exactly as a week does — a stream is a unit of work, not a date — so the test is a month followed by a day rather than a span; requiring the span is what let `(Jun6)` through. Refusal is safe precisely because it only gates *creation*; running the same patterns as a bulk dissolution would release the ~25k events that date-suffixed real initiatives already hold.
- **A roster is a selection, and the thing it must not become is a listing**: every stream the classifier may choose from is written into every prompt, so the roster's size is a function of the table it is drawn from — and that is a feedback loop, not a listing. Each stream created makes the next reuse target harder to find, the model creates a neighbour instead, and the roster grows again. It reached **1,018 streams and 329 KB per classification** while the classifier minted **~101 streams an hour, roughly one per session**: six rows named `agent-c: eval-3 <app> environment (eval-3 integration)` inside one hour, one initiative split per application. `prompt::build` therefore **selects**: `ROSTER_LIMIT` = 200 streams, ordered by proximity, rendered as `id  name — description  [tags]`. **33 KB, and it no longer grows with the table.** Every number here is measured against the live corpus and re-measurable; do not adjust one on taste. Four properties are load-bearing.
- **Proximity is measured against the session, never against now**: the ordering key is how far the session under classification falls from each stream's activity period (`ClassificationInput::started_at` against `StreamSummary::first_active`..`last_active`), zero when the period contains it, ties broken by the tighter period. **Absolute recency looks equivalent and is not**, and only a live check shows it: the classifier drains a backlog months deep, so the 23 `agent-c: eval-3 <app> environment` streams were created on one August morning and hold **April** events. Ranked by absolute recency they sit at 495–860, so a 200-stream roster showed **0 of 23** — every one of them hidden from every other, which is precisely how the family kept growing. Ranked by proximity to the April session being classified it shows **20 of 21**. A replay cannot catch this, because "newest event" leaks assignments made after the decision; the replay scored absolute recency at 99.91%. Symmetry is deliberate: a stream that continued *after* a session is as much a reuse candidate as one that preceded it. The ordering key comes from `stream_activity_windows` over `events`, **not** from `streams.first_event_at`/`last_event_at` — only `tt recompute` writes those and nobody runs it, so 758 of 1,018 streams have `last_event_at` NULL and would sort into one undifferentiated tail.
- **The cap is measured, and it is safe only because name-normalized reuse backs it**: replaying 1,165 reuse decisions, the stream the classifier actually reused ranked 1st by median, 13th at p95, 26th at p99, and fell inside the top 200 **99.91%** of the time — against 99.48% for recency-before-the-session and **54.76%** for the shipped `updated_at DESC` (which mostly records when `tt recompute` last ran, so capping *that* ordering would have hidden half the reuse targets). 200 is ~8x the p99 rank and the curve past it is flat. Capping at all is only defensible because `tt_db::find_stream_by_normalized_name` turns a name proposed for an unshown stream into reuse of that row, so **a cap can only ever cost a semantically near-duplicate, never an exact one**. The two halves were designed to compose; shipping the cap without the dedup would trade one duplicate source for another.
- **Compress the line, never the signal**: the old line spent 331 bytes a stream on `id: …; slug: …; name: …; description: …; tags: …; last active: …`. The labels are overhead, the RFC 3339 timestamp was NULL for 758 of 1,018 streams and is now carried by the ordering itself, and the slug exists on 25 streams while the model answers with an id. Descriptions average 428 bytes and reach 910, so they are truncated to `ROSTER_DESCRIPTION_BUDGET` — **truncated, never dropped**, along with tags: they are what the model recognises a stream by, and dropping them would save bytes by causing the duplicates the cap exists to prevent. The name is never truncated.
- **Selecting what the model sees is presentation; concluding from it would be attribution**: ordering and capping a roster is a rendering decision and the model still chooses, which is why this does not cross the line drawn in `tt-core/AGENTS.md`, "Streams are semantic". A rule that *derived* the stream from proximity, or from a cwd, title or app, would. The prompt states reuse as the default, creation as the exception, and that a stream is one initiative spanning many sessions rather than one row per task instance — because granularity has no mechanical signature and `is_misnamed_stream` deliberately does not judge it: `agent-c: eval-3 saleor environment` names real work by a real subject and must keep passing the guard. Collapsing streams already too granular stays `tt streams rename` then `tt streams merge`, an operator judgement, never inferred.
- **A duplicate name is impossible to create, and case is not a duplicate**: `tt_core::normalize_stream_name` trims and collapses internal whitespace, and that form is what decides whether two names are one name. One leading space is not hypothetical — it minted `" agent-c: eval-3 prometheus test-stage (round 2)"` beside its unspaced twin three minutes apart, because the reuse check was a plain string comparison against a roster snapshot. Three halves close it and each is needed: `insert_stream` and `rename_stream` normalize on write, so the column invariant holds whichever path wrote it; `find_stream_by_normalized_name` normalizes **both** sides, because the rows predating that invariant are exactly the rows most in need of being found; and it reads the **table**, not the caller's roster, because a snapshot is loaded once per pass and a pass runs for hours — two rows named `agent-c: eval-3 traccar environment (eval-3 integration)` were minted eleven minutes apart with the snapshot check in place. Both paths that mint a stream from a model-authored name owe the check: `resolver.rs`'s `stream_named` and `Database::accept_proposal`, the latter because a proposal waits in the queue for a human while the classifier keeps running. Several rows may already share a name (three groups do), so the **earliest created** wins and successive passes converge instead of alternating. **Case is deliberately preserved**: the live table holds 13 streams under `DPI:` and 7 under `dpi:`, and deciding those are one initiative is `tt streams merge` — an operator command with an audit trail — not a silent effect of writing a name. Normalization may only erase differences no human could have meant.
- **A stream minted mid-pass must carry the period it was minted for, or it is invisible for the rest of that pass**: the entry above closes *exact* duplicates, and this is why the survivors are *near* ones. A newly created stream was pushed onto the roster with `first_active`/`last_active` of `None`, and `prompt::build`'s `proximity` returns `(true, 0, 0)` for a stream with no period, which sorts behind every stream that has one; `ROSTER_LIMIT` then cuts the tail, 200 of ~1,245 on the live table. So the model could not see the stream it had just created, and named a near-miss for the same work — which `find_stream_by_normalized_name` cannot collapse *precisely because* it is not an exact match. Measured on the live table: `dojo: smart home ideation + planning` (13:07), `dojo: smart home automation ideation` (14:38) and `dojo: smart home automation ideation + planning` (20:01), three rows for one initiative inside seven hours, each splitting the same day's attention on the report. The fix is to carry the classified work's own `started_at`, threaded from both call sites. **It invents nothing**: that session *is* the stream's first activity, so this is exactly what `stream_activity_windows` reports for the stream on the next pass — one pass earlier. It is also not a judgement about granularity, which stays operator work: this only decides what the model is *shown*, and a crude prefix match over the same table flagged 14 pairs of genuinely distinct `agent-c` work, which is why collapsing near-duplicates remains `tt streams rename` then `tt streams merge` and is never inferred.
- **A stream id from the classifier is untrusted input; validate it before it reaches a write**: the roster handed to the classifier is a snapshot, and `tt streams dissolve` deletes rows behind it, so `StreamChoice::Existing { stream_id }` can name nothing by the time the verdict lands. `events.stream_id` is a foreign key, so writing it raises `FOREIGN KEY constraint failed` — which aborted a live pass after 141 sessions and left every candidate queued behind it unclassified. `Resolver::resolve` therefore gates the whole `Existing` arm on `Database::stream_exists` (id only: `events.stream_id` stores the literal string, so resolving a slug or a name would silently rewrite the answer instead of refusing it). A missing id is **refused**: counted in `refused_missing_stream`, logged at `warn` with the offending id, candidate left unassigned. Not substituted, not junked (junk means "no attributable work"; this is work whose container vanished), and above all not proposed — `proposals.proposed_stream_id` has no foreign key, so a bad id lands there silently and only fails at accept time. Refusing is kept separate from `refused` because the two name different defects: a name that describes no work is the classifier inventing a container, a vanished id is dissolution editing the roster underneath it.
- **Whitespace inside a returned stream id is normalized away; nothing else about it is**: the model emits ids with whitespace in them, and refusing those threw away correct verdicts. Observed live in three hours: `" eb2754ad-e9a3-469b-bdb3-1768bc8860e8"` (leading space) resolves to `dojo: smart home ideation + planning`, and `" e638ad6d -fd e6 -4f 85 -b 9d 0-7 e9 b0 2b 98 9a8 "` (spaces sprinkled through) resolves to `agent-c: gdrive paths review` — 3 of 5 sampled refusals named a real stream. Each cost a model call and left the work unassigned. The `Existing` arm therefore strips whitespace before `stream_exists`, under the same rule `normalize_stream_name` follows for names: **normalization may only erase differences no human could have meant**, and a space inside a uuid is such a difference. It is deliberately *only* whitespace. A short id is still refused even when it is an unambiguous prefix — `"ff383f53"` is the 8-char form `tt report` renders, and it prefix-matches `devbox: infra`, but accepting a prefix is *resolving an ambiguous reference* rather than normalizing one, and two ids sharing a prefix would bind work to the wrong stream silently. A malformed uuid and one naming a dissolved stream stay refused for the same reason: the candidate is left unassigned, where it reads as classification lag.
- **A half-answered verdict is kept, and a declined one is a verdict too**: `ClassificationExtract::try_from` used to demand a name *and* a description before it would build a `StreamChoice::New`, so a model that named the work but skipped the description produced a hard `LlmError::Parse` — the session counted as an error and stayed unassigned. One live pass lost 315 sessions that way. The name is the load-bearing half: it is what `is_misnamed_stream` judges and what the stream is filed under, so `StreamChoice::New.description` is an `Option` and a missing one is carried as absent. **Absent, never a placeholder** — `tt streams describe --backfill` selects streams whose description is null, so a fabricated one would file the stream as described, exile it from the command built to finish the job, and feed the fabrication back to the classifier in every later roster. `tt_db::NewStreamProposal.description` is optional for the same reason, since a proposal's payload is only parsed at accept time and a shape the accepter rejects would sit in the queue looking answerable. This file used to say the *other* half must never be softened — that an answer naming neither a `stream_id` nor a `new_stream_name`, with no `throwaway`, is a model that failed to answer. That was wrong, and it was wrong against this repo's own prompt, which instructs the model to decline rather than invent a container when it cannot identify the work. Obeying that instruction produces exactly the all-null extract, and rejecting it took **100% of classifications** down: `classifier_consecutive_failures` reached 53, `classifier_retry_delay` is exponential and capped at five minutes, and the daemon's classify loop managed **0 sessions in 7 minutes** against a ~3,800-session backlog. A well-formed all-null answer is therefore `StreamChoice::Undetermined` — see the entry below. What genuinely stays an error is output that does not deserialize at all: there is no answer to read, and `transport::retrying` redraws it because the next sample may fit. A description with no name stays an error too, being the dependent half of a choice whose load-bearing half is missing; nothing in the prompt invites that shape. Refusal of a *name* that describes no work is likewise unaffected, because the guard reads the name alone.
- **"I cannot determine this" is a verdict, and it is not junk**: `StreamChoice::Undetermined` is the model reporting that it was reached, it answered, and it could not identify the work. Three things follow and none is negotiable. It is **not an error**: `Resolver::classify` only records a failure on `Err`, so an undetermined answer never touches `outcome.errors`, never calls `record_classifier_failure`, never drives `classifier_consecutive_failures`, and never arms the failure backoff — it also calls `record_success`, because the call succeeded, which is what clears the counter and keeps the classify loop running. It is **not junk**: `Throwaway` asserts no attributable work exists and routes the session to the junk stream, while undetermined asserts nothing at all, so conflating them files real work as nothing — they are separate variants, separate resolver arms, and separate counters for exactly that reason. And it is **not a container**: the session is left unassigned, where it reads as classification lag, which is the same treatment `refused` and `refused_missing_stream` already get. It is counted in its own `undetermined` bucket and reported in the pass summary beside `errors`, never inside it, because a prompt working as instructed on unidentifiable input must not read as a defect. **No suppression state is recorded.** An undetermined session stays a candidate, so new events, a fuller roster, or a better prompt can still place it later; the daemon does not spin on it because `should_drain` already re-arms only when some candidate the pass looked at is *gone*, which is the mechanism built for passes whose every verdict is refused. If `undetermined=N` grows large enough to crowd the recency-ordered head of a pass, that is evidence to fix at the source — more fetch budget, better roster — not a marker to hide it behind.
- **An exhausted fetch budget has to stop the model, not merely inform it**: the budget's own answer is a *tool result*. `FetchOutcome::BudgetExhausted` renders text telling the model to answer from what it has, and the model was free to read that and call a tool again — which it did, each extra call spending one of rig's `max_turns` until the run hard-errored. `MAX_MODEL_TURNS = MAX_FETCH_CALLS + 2` reads like two spare turns and is one: four fetches take four turns, answering takes the fifth, so the sixth bought exactly one post-exhaustion tool call before the bound. On the live daemon that was `classifier_last_error: PromptError: MaxTurnsError: reached max turns` with `classifier_consecutive_failures: 4`, and the exponential `classifier_retry_delay` those failures armed had cut the drain from **1.67 to 0.17 classifications a minute** — roughly 390 hours for a 3,900-session backlog. Two halves fix it and both are load-bearing. **The cause is `WithdrawSpentTools`**, a `StepEvent::CompletionCall` hook that patches `RequestPatch::active_tools([])` on every turn after the budget is spent; the Anthropic request omits `tools` entirely when the set is empty, so an exhausted budget becomes a property of the request instead of advice the model may decline. Do *not* patch a `tool_choice` alongside it — rig fails a request closed when the effective choice names a tool the allow-list dropped. **The symptom is `StreamChoice::TurnsExhausted`**, read structurally off the `PromptError::MaxTurnsError` variant (never off rig's rendered `reached max turns limit: 6`, which is rig's prose to reword) and returned as an `Ok`, not an `AttemptFailure`: nothing failed, so it must never reach `errors`, `record_classifier_failure`, or the backoff, and nothing a redraw would fix, since a retry opens a *fresh* fetch budget and would pay another whole turn budget to not converge again. It is a sibling of `Undetermined`, not a synonym: both rest unassigned, but a decline asks for nothing while a spent turn budget says the agentic loop failed to converge, so `turns_exhausted` is its own counter. Raising `MAX_MODEL_TURNS` is the tempting lever and the wrong one — it buys the same non-answer for more model calls, and with the hook in place five turns is provably sufficient. `BudgetExhausted` stays as the within-turn backstop, because one turn may emit several tool calls at once and the last of them can still cross the bound.
- **A proposal escalates a question; it must never retire the machine's ability to answer it**: this entry used to say the opposite — that `unclassified_user_sessions` and `get_pending_proposal_for_events` hold a candidate back because *a human owns the answer now*, and that the only exemption is a proposal naming a dissolved stream, which nobody can accept. The exemption was right and the rule around it was wrong. A proposal is not an answer, it is a question waiting on a reviewer, and reviewers are the scarce resource this product exists to conserve — so "a human owns it" in practice means "nobody will ever look at it", and the block became permanent exile. Measured on the live database: **731 pending proposals, none above the 0.80 threshold, authored 2026-08-02..08-07, blocking all 37 August candidate sessions and 157 of 185 July ones.** Meanwhile the classifier that wrote them materially improved — roster cut from 1,018 streams to 200 ordered by proximity, a `summary` field it had been missing, agentic mid-classification fetch. Unblocking 25 of the frozen July sessions and replaying the *current* classifier placed **13 of the 17 it reached at ≥0.80, ~76%**; the freeze, not the ambiguity, was what kept them unattributed. **A pending proposal never permanently blocks a candidate.** `unclassified_user_sessions` reads no proposals at all, and a window run whose queued answer came from an *earlier* classifier is asked again.
- **What the block was also doing is kept, and moved to where a proposal is filed**: it stopped a bounded pass queueing a duplicate question every few minutes, which is real. That job is now `has_pending_proposal_for_session` / `get_pending_proposal_for_events`, consulted by `Resolver::propose` rather than by selection, so the guard survives and the exile does not. Two outcomes, and neither is negotiable. **A verdict at or above the threshold assigns, and supersedes the queued proposal** — `Resolver::assign` is the single funnel every write of a stream passes through, junk included, so once the events carry a stream the question is spent and `ProposalStatus::Superseded` records that. **A verdict below the threshold changes nothing**: the pending proposal is left byte-for-byte as it stands, no second proposal is filed, and the candidate is counted in `skipped`. Genuinely ambiguous work keeps waiting for a human, and waits behind exactly one row. The read side stays narrower than the write side on purpose: a proposal naming a dissolved stream suppresses nothing, because no reviewer can accept it, but a confident verdict still supersedes it, because it is a question about this target and the answer has landed.
- **Re-asking is conditional, because the freeze and the unconditional re-ask are two failures and not one**: removing the pre-call skip from `classify_window_runs` fixed the entry above and immediately created its mirror image. The loop it opened runs once per pass: the phase takes the newest `WINDOW_RUNS_PER_PASS` unassigned runs, **spends a model call on each**, most answer below the 0.80 threshold because a run's payload is a handful of window titles rather than a session's prompts, `Resolver::propose` finds the pending proposal and files nothing, the run stays unassigned — so it is still in the newest-first list next pass and is asked again, identically, forever. Measured live: **212 pending window-run proposals accruing at 1–2 a minute against a budget of 101 calls a pass**, while **71,635 focus events across 149 days** sat unattributed because the budget never reached past them. Focus events are direct time, which this file says is the answer whenever the user asks where his time went, so the waste is not merely money: the bounded phase built to keep the headline number current was spending itself on questions already on file. **Neither extreme is available.** Skipping a queued run forever exiles it from a classifier that keeps improving; asking it every pass burns the budget that answers everything else. `tt_llm::CLASSIFIER_GENERATION` is what makes the two separable — a proposal records the newest generation that answered it, and the gate skips a run **only when that generation is the current one**. So a question this classifier has answered costs nothing, and a bump re-opens every queued question at once.
- **The generation is a `const` in `tt-llm` and it must be bumped by hand, which is the point**: it sits in the crate root beside the prompt, the roster and the model, because those are exactly the changes that invalidate an earlier refusal, and a maintainer editing them should be looking at it. Bump on any material change to the prompt, roster construction, model, or fetch behaviour; a reworded log line or a behaviour-free refactor does not qualify. The precedent is the 731-proposal incident above: the classifier had materially improved and **nothing in the data said so**, so every queued question read as current. `NULL` — every row written before the column existed, the 212 included — matches no generation, so those are re-asked exactly once rather than grandfathered in, which is the right treatment for a verdict whose author cannot be identified. It is deliberately not a config key and not derived from a prompt hash: a hash would bump on whitespace and re-ask 212 questions for nothing, and a config key invites tuning a correctness marker.
- **Exactly once is a property of the write, not of the read**: the gate alone would re-ask a stale proposal on every pass, because refusing again leaves the row exactly as stale as it was — the same loop, just entered through a different door. `Resolver::propose` therefore stamps the current generation onto the pending proposal it declines to duplicate, so a bump costs one pass over the queue rather than an unbounded number. Stamping is **bookkeeping and never a verdict**: status, stream, confidence and reasoning are untouched, the row stays `pending` for its reviewer, and it does not bump `db_version` because it changes no assignment. Writing `rejected` to achieve the same suppression is forbidden and always will be — that is a human verdict `has_rejected_proposal` reads, and manufacturing one silences the classifier on that target for good, which is the failure this whole area exists to undo. The stamp is applied uniformly across scopes even though only the window-run gate reads it back, because the column has one meaning — the newest generation that answered this question — and stamping one scope and not the other would give it two.
- **The gate is a window-run rule and is not extended to sessions, on an asymmetry in the data**: a run's identity *is* its exact event set, which is what `proposals.event_ids` is keyed on, so a run that gains an event stops matching its proposal and is re-asked with no generation bump at all. That makes the skip narrow by construction. A session has no such property: it keeps its `session_id` while its prompts grow, and `get_recheck_candidates` reads only sessions already *classified*, so an unassigned session carrying a pending proposal is covered by nothing. A pre-call session skip would therefore freeze a lengthening session — one whose next call might well succeed on the new prompts — until somebody bumped a constant for unrelated reasons, and that is the freeze this area just removed, re-created on a slower clock. The session duplicate guard in `propose` is unchanged in what it *decides*; it only gained the stamp. `a_session_whose_answer_is_queued_is_still_re_classified` guards the decision.
- **The skip has its own counter because a conserved budget and an idle pass look identical**: a pass whose whole window-run budget went to skips moves `assigned`, `proposed`, `superseded` and `errors` not at all, and would read as a pass that found nothing to do. `AutoClassifyOutcome.skipped_answered` is reported in the summary line beside `skipped`, and the two are deliberately separate: `skipped` counts answers that **cost a model call** and then added nothing to the queue, while this one counts calls not spent. Folded together, the line could no longer say whether the budget was saved or burned. **`should_drain` is unaffected**: it compares `unclassified_user_sessions` before and after a pass, a `window_focus` row carries no `session_id` and so can never enter that set, and the gate changes neither which sessions the session phase selects nor what happens to them. A skipped run is one more thing that can outlive a pass unseen by the probe, which errs in the direction the probe was built to err — an unseen leftover makes the loop wait for the next trigger rather than spin — and focus inflow arms classification on its own through `import_local_events` every ~30s.
- **`superseded` is not `rejected`, and manufacturing a rejection is still forbidden**: rejection is a *human* verdict that `has_rejected_proposal` and `has_rejected_new_stream_proposal` read to suppress future answers, so writing one on the user's behalf both falsifies the record and silences the classifier on that target for good — the exact failure this change exists to undo, re-created one row at a time. `Superseded` is read by neither. It is also not `accepted`: acceptance writes `assignment_source = 'user'` and only `tt proposals accept` does that. `ProposalStatus::from_db` errors on an unknown string, so the variant is load-bearing in **both** directions — omit the parse arm and `tt proposals ls` fails on the first superseded row. Superseding **does not bump `db_version`**: it changes no assignment of its own and only ever follows one, and that write has already signalled the daemon. There is no bulk surface and must not be: a proposal is retired only as a consequence of the classifier confidently answering that specific target, which is what `tt classify --auto`'s guards make safe. The pass summary carries `superseded=N` beside `proposed=N` because it is the one count that says the review queue shrank without a human touching it — a reviewer seeing fewer proposals than yesterday needs to know whether they were answered or lost.
- **Stranded proposals still get their own handling, for a different reason**: `proposals.proposed_stream_id` has no foreign key, so `tt streams dissolve` leaves rows nobody can accept. `PROPOSAL_IS_ANSWERABLE_SQL` keeps those from suppressing a fresh proposal, and `tt proposals ls` renders one `(gone) <id>` with a footer rather than as a bare uuid indistinguishable from a real unnamed stream. The **writer** half is now there too, and the two commands differ because their claims differ. `tt streams dissolve` asserts *this was never work*, so there is no target to re-point to: it **names** every pending proposal it strands — id, stream, event count — in `--dry-run` as well, since that is where the operator decides, and changes not one byte of them. `tt streams merge` asserts *this was work, on a different row*, so a proposal naming a merged-away source has an obvious correct home and is **re-pointed at the target inside the existing transaction**. Re-pointing preserves the classifier's verdict exactly as re-pointing events does, and is order-independent: accepting-then-merging and merging-then-accepting land the same events on the same stream. Only `status = 'pending'` rows move — an accepted, rejected or superseded proposal is a historical record of a decision and must never be rewritten. `proposals_repointed` participates in the existing `db_version` bump because re-pointing changes what accepting would *do*, unlike supersede and stamp, which are bookkeeping that follows a write. Measured live before this existed: dissolving one stream would have silently stranded 9 proposals covering 125 events, and merging the same stream re-points 19.
- **A review queue is spent attention, so it is ordered by the attention it resolves**: `tt proposals ls` is where a human answers what the classifier would not, and that human's day is the resource this whole product exists to conserve — so the order the queue presents its items in *is* the product. `get_proposals` orders `created_at ASC`, which front-loads the stalest question and says nothing about what answering it is worth. Measured on the live queue of **the 12 proposals resolving the most attention carry 27.5% of all attention waiting in the queue, the top 20 carry 36.4% and the top 50 carry 56.9%** (measured 2026-08-08 over 421 pending; an earlier measurement of 477 pending read 41.8% for the top 12, and the figure moved because the pane release changed which events are unassigned — re-measure rather than quoting either): a reviewer who answers 12 items instead of 477 attributes nearly half the unattributed direct time. Age-ordering spends that reviewer at random. `Database::pending_proposals_by_attention` is what the command reads, and it is a **second view rather than a change to the first** — `get_proposals` keeps its ordering because `tt proposals accept`/`reject`, `tt status`'s drift verdict and the dashboard rail all read it, and none of them is a review queue. Attention is counted in **events, not milliseconds**, because a proposal is answered *before* its events are allocated: allocation needs a stream, and supplying one is exactly what the reviewer has not done yet. The three types counted (`user_message`, `window_focus`, `tmux_pane_focus`, held in `ATTENTION_EVENT_TYPES_SQL`) are precisely the ones that open a direct-time interval, which is the same rule as "Where did my time go" above; counting agent activity would rank a proposal by how busy the machine was rather than by how much of the reviewer's own day it explains. Three properties are load-bearing. It is a **re-ordering and never a filter**: a proposal resolving no attention is still a real question and sorts last rather than disappearing, and one naming a dissolved stream is listed *and* still flagged `(gone)` — `PROPOSAL_IS_ANSWERABLE_SQL` is deliberately not applied here, because `tt proposals ls` is where a reviewer learns such a row exists at all. Ties fall to `created_at ASC` and then the id, so equal attention presents in one stable order and the snapshots stay deterministic. And it **writes nothing**: ranking a queue must not assign, supersede, reject or stamp a single row — see "A read command must not write" above.
- **Fetching is bounded, filtered, and never mandatory**: the classifier may pull more of a session mid-classification, because deciding in advance how much of a session is enough is what produced bad verdicts on ambiguous input — 601 unclassified sessions share the byte-identical prompt `The following tool was executed by the user` and carry 566 distinct summaries between them, so from the fixed payload they are one indistinguishable string. Three invariants hold it together. **Bounded**: `MAX_FETCH_CALLS` caps a classification at four fetches, and exceeding it is a clean `FetchOutcome::BudgetExhausted` telling the model to answer from what it has — never an error, because a verdict reached under a spent budget is still a verdict, and a model that cannot reach one answers with low confidence and leaves the session unassigned. That answer alone stops nothing, so the bound is enforced twice: within a turn by that outcome, and between turns by `WithdrawSpentTools`, which stops advertising the tools at all — see "An exhausted fetch budget has to stop the model" above. **Filtered**: `SessionTools::new` takes the injection predicate as a required argument and `fetch.rs` applies it to every fetched message, so a new `SessionDetail` implementor cannot forget it. **Optional**: a payload that already names the work spends nothing, which is what keeps the bill bounded in aggregate. The fetch set is deliberately two methods and every exclusion was measured — read the module docs on `tt-llm/src/session_detail.rs` before adding a third. Tool-call names and touched file paths in particular are *not* available: `tool_call_timestamps` is an in-memory `AgentSession` field that is never persisted, and the `events` table has no payload column, so an `agent_tool_use` row records that a call happened and never which tool or which file.
- **Both classification paths retry off-schema output, and a status that means *not now***: `RigClassifier::extract` has always redrawn a sample whose output missed the schema, but `classify_with_tools` was added without it and made a single attempt, which is very likely how parse failures accumulated into the hundreds. Both now go through `tt_llm::transport::retrying`, which is why the split lives in one place: `AttemptFailure::Malformed` (a deserialization failure — the next draw may fit) is retried up to `MAX_PARSE_ATTEMPTS`, `AttemptFailure::Http` is judged by `HttpFailure::is_transient`, and `AttemptFailure::Failed` (a failure carrying no status at all) is returned at once. The agentic path opens a **fresh fetch budget per attempt**, not per classification, because rig starts a new conversation each time and a retry remembers nothing the previous attempt fetched — reusing a spent budget would make the retry blind while still costing the same bounded `MAX_MODEL_TURNS` round trips. The **wait** budget is the opposite, and deliberately so: it is spent across the whole classification and never reset, because its purpose is that no one session can stall a pass.
- **Transport retry was once forbidden here, and what changed is the evidence, not the appetite**: this file used to say never retry API, network, or rate-limit errors, because `LlmError::Api(String)` carried no status code and nothing could tell a spent quota from a transport blip. That reasoning was right and is now obsolete. rig exposes the status *structurally* — `provider_response_status` walks `StructuredOutputError` → `PromptError` → `CompletionError` → `http_client::Error` and returns the `http::StatusCode` the Anthropic provider stored when it built the error from a non-2xx response — so `HttpFailure` carries a number and `LlmError` grew an `Overloaded` variant to carry it out of the crate. This mattered in production: a live drain sat at **0.65 sessions/min** with `classifier_last_error` reading `HttpError: Invalid status code 529`, and **529 is Anthropic "overloaded"** — explicitly retryable — so every occurrence was costing a session its classification for a condition that clears in seconds. Do **not** re-derive the status by matching `"529"` out of the rendered message: the prose is the provider's to reword, the status is a protocol number, and a policy keyed to prose is the trap the typed path exists to remove. `HttpFailure::is_transient` is the only place the *status* line is drawn — 429 and every 5xx are the provider saying *not now*; every other 4xx (bad request, rejected key, spent quota) is it saying *not this*, and is returned immediately with no retry and no wait. A failure carrying no status is never guessed at — with exactly one exception, below, and it is not a guess.
- **A model call that cannot end is worse than one that fails, and every call here once could not end**: `anthropic::Client::new(api_key)` takes rig's default HTTP backend, `reqwest::Client::default()`, whose timeout is **`None`**. Nothing in this repo configured one, so a connection Anthropic accepted and never answered blocked its classification *forever* — and because a pass classifies serially, blocked the pass with it. Measured on the live process: **3,077 seconds alive at 0.0% CPU**, 40 MB RSS, **one** open TCP connection, **3 sessions classified in 20 minutes** against a healthy 3.9/min, putting the remaining 3,687 sessions ~410 hours out. Every completing call resolved a candidate, so throughput was purely latency-bound; the classifier was not broken, it was waiting. **The seam is rig's own and rig documents it**: `Client::new`'s doc comment says callers wanting a different backend "should go through `Client::builder` and chain `ClientBuilder::http_client` before `ClientBuilder::build`", which is all `timed_client` does — the same default backend, with the one setting that was missing. Only the overall `.timeout()` is set; it already covers connect, response and body, so a separate `connect_timeout` would be a second knob answering the same question. **`REQUEST_TIMEOUT` is 120s and the number is set above the slowest real work, never near the typical**: a bound that kills completions the provider is genuinely serving is worse than none. The slowest *whole* classification ever observed completing ran ~92s (0.65/min), and a single request cannot exceed the classification containing it, so 120s sits above every request that has ever been served here while cutting the measured hang by 25x. This is why `reqwest` is a direct dependency of `tt-llm` pinned to the 0.13 rig resolves.
- **A timeout is transient, and it is recognised structurally or not at all**: silence is the provider saying *not now* just as plainly as 529, and more so — a 5xx is a refusal, whereas a timeout means nothing about the request was refused. So it routes through the *existing* `retrying`, shares the same `TransportBudget`, the same 4-retry cap and the same 20s cumulative wait; a second retry mechanism would be a second set of bounds to get wrong. `AttemptFailure::Timeout` is its own variant rather than an `Http` carrying a synthetic 504 or 408, because **the provider set no status** and inventing one is the prose-matching sin in reverse — it would fabricate provider evidence inside the type built to carry only real provider evidence. Recognition is `timed_out` in `rig_classifier.rs`, and it is structural twice over: it walks `std::error::Error::source()` rather than matching rig's variants (that chain's shape is rig's to rearrange, and a timeout can surface from any link that does I/O — sending the request or reading the body), and the verdict at the end is `reqwest::Error::is_timeout`, which walks its *own* sources for a `TimedOut` marker, a timed-out hyper error, or `io::ErrorKind::TimedOut`. Do **not** match rig's rendered `Http client error: operation timed out`: that is prose two crates may reword. A downcast is the only way in, because rig erases the error to `http_client::Error::Instance(Box<dyn Error + Send + Sync>)` and reqwest's `TimedOut` marker is private — which makes **one** reqwest in the dependency graph load-bearing, since two copies make the downcast silently fail and the hang non-retryable again. The guard is that the timeout tests build their error through rig's real transport against a local never-answering socket, so a split graph fails them rather than passing quietly. A statusless error that is *not* a timeout (a connection reset) stays terminal; the status still wins when there is one.
- **A per-request bound is not a per-classification bound, and the product is the reason `Deadline` exists**: bounding one request leaves the multiplication untouched, because an agentic attempt is up to `MAX_MODEL_TURNS` (6) requests and a classification is up to `1 + MAX_TRANSPORT_RETRIES` (5) attempts. 5 × 6 × 120s ≈ **72 minutes on one session**, and 200 of those is a **241-hour** pass — finite, and unacceptable. `MAX_CLASSIFICATION_MS` caps the whole classification at **300s**, which brings the worst-case pass to **~16.7 hours** (against *never terminates* before either bound). The number is measured, not taste: a healthy drain ran 3.9 classifications/min (~15s each) and the slowest rate ever seen *while still completing* was 0.65/min (~92s), so 300s is 3.3x the slowest classification the provider has actually served and still fits three consecutive attempts at that rate. It is enforced in two places because one is not enough: `retrying` refuses to *start* an attempt with nothing left, and `RigClassifier::within` wraps each `block_on` in `tokio::time::timeout(remaining)` so an attempt cannot outlive the allowance mid-flight — checking only between attempts would let one attempt spend `MAX_MODEL_TURNS × REQUEST_TIMEOUT` while every individual request stayed inside its bound, which is the same mistake one level up. A classification cut off here leaves its session **unassigned**, exactly where a failed one already leaves it: still a candidate, re-reached next pass. So the ceiling is deliberately a backstop against pathology and not a service target — abandoning one session costs a session, while blocking on it costs the pass. Raising `REQUEST_TIMEOUT` is the tempting lever when a slow provider trips this, and it is the wrong one: it buys a longer hang, not a better verdict.
- **All three retry bounds are numbers, and all three are ceilings on a whole classification**: at most **4 retries** (five transport attempts), at most **20 seconds** of cumulative wait, and at most **300 seconds** of wall clock. The wait ladder is 1s/2s/4s/8s capped at 8s per step and jittered to half-plus-random so a pass that met one outage does not send every queued session back in lockstep. The numbers are picked against a baseline session that takes roughly 90s and against the alternative of losing it: 20s is a fifth of a session to save one, and it also bounds the bad case, since a wholly unreachable provider adds at most that per candidate and a `SESSIONS_PER_PASS` pass still terminates. A `Retry-After` is honoured verbatim rather than jittered — the provider named a time and second-guessing it re-forms the herd — but is refused when it would not fit the remaining allowance, because a provider asking for longer than a session is worth is exactly the stall the cap exists to prevent. A timeout consults no `Retry-After`: a provider that said nothing said nothing about when to come back, so the ladder decides. rig 0.40 keeps a failed response's status and body but **drops its headers**, so nothing supplies `Retry-After` today; `HttpFailure` carries the field anyway because it is the provider's own answer to the question the ladder guesses at. Do not parse it back out of the body — that is prose matching wearing a different hat.
- **The pass summary must keep overload separate from breakage, and silence separate from both**: `ErrorCauses` buckets failures by `LlmError` variant, and `overloaded` is its own bucket rather than part of `api` because the two ask different things of whoever reads `errors=N (…)`. A run degraded by provider overload recovers by itself and its candidates are worth re-reaching next pass; a run hitting terminal errors will hit them identically and needs someone to look. Folding them together is how a provider outage came to look like a classifier defect. A bare `errors=315` with no breakdown was the original defect and the reason these buckets exist at all. `timeout` is a fifth bucket for the same reason it is not folded into `overloaded`: both are worth re-reaching, but they are different observations and point at different things to check — a 529 proves a model was reached and is answering, so `overloaded=180` is a capacity question, while `timeout=180` says nothing came back at all and is a connectivity question, or a session whose agentic loop cannot finish inside its allowance. `undetermined=N` is reported as its own field *outside* `errors` rather than as another cause, because it is not a failed call at all — no `LlmError` exists to bucket. `turns_exhausted=N` sits beside it for the same reason and one more: it is the field that says the agentic loop is over-fetching, which is a different thing to act on from a prompt that declined, so the two must never share a counter.
- **Classifier health is recorded per call in both directions, because the counter it feeds is read as *consecutive***: `record_failure` always wrote immediately, but success was written once, after all four phases of `run_auto` returned. A pass is bounded at 200 sessions and runs for hours, so the pair was asymmetric and `classifier_consecutive_failures` actually meant *failures since the last completed pass*. The live daemon showed the shape exactly — the counter at 3 and `classifier_last_success_at` a day old, while it was classifying successfully at that moment — which arms the exponential `classifier_retry_delay` against a provider that is answering, the same throttle that once cut a drain to 0.17 classifications a minute. `Resolver::record_success` therefore mirrors `record_failure`: one write per successful call, and like every health write it does **not** bump `db_version`. Deferring it again to save a write per session trades a row nobody notices for a backoff nobody asked for. Observing the regression needs the resolver directly; through `run_auto` the end-of-pass write hides it, which is why the test drives `Resolver::classify` twice.
- **The classify loop's model calls run concurrently and its writes do not, which avoids the blocker rather than solving it**: this entry used to close the option. The dominant unassigned population was **1,339,657 events across 3,559 sessions awaiting classification**, draining at roughly one session a minute — about 59 hours unattended — and bounded concurrency was the only lever on it and was deliberately not taken. **The blocker named then is still real and still unfixed**: `stream_named` in `classify_auto/resolver.rs` checks and then inserts as **two separate operations** — roster, then `find_stream_by_normalized_name`, then insert — so two concurrent copies would both find nothing and both insert, re-creating the duplicate-stream failure that took 55 renames, 5 merges and 9 dissolves to clean up and that the DB-authoritative name check exists to prevent. Making *that* safe still means one transaction around the find-and-insert, and a unique index still cannot serve, because duplicate names legitimately exist in the table (three groups share one) and `find_stream_by_normalized_name` is written to resolve them by earliest-created rather than to forbid them. **What changed is that nothing runs it concurrently.** `classify_sessions` splits a pass in two: a chunk of `CLASSIFY_CONCURRENCY` (8) inputs is answered inside one `std::thread::scope`, and every verdict is then applied one at a time, in the chunk's own order, on the single connection the resolver holds — so `stream_named`, `assign`, `propose` and `inherit` are exactly as serial as they were. A model call is 15–90 seconds of waiting on Anthropic, so a chunk now costs the longest wait in it instead of the sum. The separation is **compiler-enforced rather than remembered**: `tt_db::Database` is `Send` but not `Sync`, so a closure reaching for the database inside the scope does not compile, and the only things that cross are the classifier — `Send + Sync` by its own trait bound — and a shared roster slice. Junk is settled before any call, since structure alone judges it. Health stays one write per call in both directions through `Resolver::record_call`, the funnel the serial and chunked paths share so the two cannot drift apart on a counter read as *consecutive* failures. A worker that panics is joined rather than left to take the scope down, turned into an `LlmError::Api` and counted, costing its own session and no other. **`busy_timeout` was never the blocker**: `Database::open` sets 30 seconds (`tt-db/src/lib.rs`), so concurrent writers would wait rather than fail; reading `PRAGMA busy_timeout` through the `sqlite3` CLI reports 0 only because that CLI opens its own connection without tt's setting.
- **A chunk answers from the snapshot it began with, and that is safe only because the roster is a cache**: every call in a chunk is handed the same roster, so a stream minted by verdict `k` is missing from the roster that verdicts `k+1..N` of that *same* chunk answered against. It costs nothing, because `stream_named` treats the roster as a cache and the `streams` table as the authority: a name it cannot find in the snapshot goes to `find_stream_by_normalized_name`, which reads the table and returns the earliest-created match, so several verdicts naming one stream collapse onto one row instead of minting several. Chunk `N+1` sees that stream in the roster regardless, because `resolve` pushes every stream it mints onto it. `one_chunk_naming_one_new_stream_many_times_creates_it_once` pins that, and `a_chunks_calls_all_run_at_the_same_time` is the only test that fails if the calls ever go serial again — forced serial it fails in 35.01s where it passes in 0.01s, because every other test decides the same thing either way. **`CLASSIFY_CONCURRENCY` is not a guard and no guard depends on it**: 8 bounds what one pass points at the provider at once, since every call in flight competes for the same rate limit and a 200-wide burst would spend the retry allowance on congestion this process created. Raising or lowering it changes how long a pass takes and nothing about what a pass decides.
- **Event writes are additive, so extractor changes need a prune**: `insert_events` is `INSERT OR IGNORE`, which means a correction to what counts as a user message adds the right rows and leaves the wrong ones forever. `tt ingest sessions` therefore feeds every session's freshly derived timestamps to `Database::prune_user_message_events`, which retires the rest. Only the machine holding a session's transcripts can re-derive it; a replica of another machine's events converges via `tt sync <remote> --reconcile`. Any future change to what a `user_message` means owes the same two steps.
- **One agent session is recorded several times, and a synced copy must not take its stream away**: the machine holding the transcript derives a session as `source = opencode` with an id like `<session_id>-session_start`, carrying the stream once classified. Every machine that syncs it in adds its own copy as `source = remote.agent` with an id like `<machine_id>:remote.agent:agent_session:<ts>:<session>:<action>`, carrying **no stream**, because attribution happens locally after the sync. The id shapes differ, so `insert_events`' `INSERT OR IGNORE` cannot collapse them, and every copy shares the session's start timestamp. Measured live: **208,619 `agent_session` rows against 117,039 distinct (session, action, timestamp) triples — 80,021 duplicate groups, 12,474 of them where an unassigned copy shadows an assigned one.** `allocate_time`'s `"started"` arm re-inserted unconditionally, so the last copy processed won and the session's whole delegated span fell to `(unassigned)`: **287 streams reported zero delegated time while holding 295,361 `agent_tool_use` events between them.** The arm now refuses only the losing case — an unassigned copy never overwrites a stream already known for that session, while any copy that does name one still updates it, so a genuine re-attribution is unaffected and a session nobody ever classified still accrues to unassigned. **This changes attribution, never totals**: the time was always counted, just credited to the wrong row. On the live corpus a `--force` recompute moved summed stream delegated from **10,136h to 14,648h** and cut zero-delegated streams from 287 to 165; on 2026-03-03..05 alone, 175h moved off `(unassigned)` onto 20 real streams while direct time stayed at 20h 16m to the minute. Direct time is untouched by construction — verified unchanged on the Jul-13 week (74h 20m) and Jul 22 (12h 19m). The remaining 165 are mostly **not** a defect: **142 of 166** are streams whose sessions also carry a `started` event naming a *sibling* stream that does hold delegated time, so the span is counted — on the other row. `agent-c: rl-eval` is the clearest case: its 105 sessions have 210 `started` events, 105 naming it and 103 naming other streams, and the largest sibling (`agent-c: env config/typing/build roadmap`) holds 57h. That is genuine ambiguity in the data rather than loss, and the allocator resolves it by last-write-wins. **Do not "fix" it by refusing an ambiguous session**: unlike the pane and session-membership passes, where refusing leaves work unassigned and honest, refusing here would strip hours off a real stream and hand them to `(unassigned)`, making the report worse. Choosing differently between two real streams is a human judgement, not an inference the allocator should make. The 24 that remain after that are unaccounted for.
- **A premature `ended` event loses a session's whole span, and the obvious fix inflates delegated time 5.5x — do not retry it without the timeout bound**: a remote exporter re-reports a running session on every observation, so a long session accumulates dozens of `agent_session` `ended` rows with distinct timestamps (one traced session has **131**, spanning 15:14 to 02:29), and the first can land before any work. `allocate_time`'s `"ended"` arm honours it, sets `session.ended`, and the `AgentToolUse` arm then skips every later tool use as belonging to a finished session. Live: **418 sessions have their first `ended` before their first tool use, covering 28,535 `agent_tool_use` events.** The loss is real.
- **The tempting fix is to defer to `agent_sessions.end_time`, which the allocator already receives as `session_end_times`, and ignore an `ended` that precedes it. It was built, measured on the live corpus, and reverted.** The traced case looks unambiguous — authoritative end 02:29:19.974, last `ended` matching it exactly, spurious first at +241ms, every tool use inside the window — but the population does not behave like the sample. **Sessions stay open for months**: `ses_201a471e0f` has an authoritative span of **2,189 hours against 55 hours of tool use and 44 tool calls**, and `ses_0e061bbf7f` spans **833 hours around a single tool call**. Running the delegated interval from first tool to that end credited those spans in full, taking summed stream delegated from 14,648h to **80,161h** and the current week from 428h to **2,116h** (leverage 5.2x to 25.9x). Direct time was untouched throughout, which is exactly why the inflation is easy to miss if you only check that.
- **What a correct fix needs**: `config.agent_timeout_ms` (30 min) already bounds an unclosed session at `last_tool + timeout`, applied in the `final_attributions` path. The `ended`-event path has no such bound, so any fix there must cap the interval at `min(authoritative_end, last_tool + timeout)` rather than trusting the end time alone. That changes the duration semantics of *every* closed session, not just the premature ones, so it needs its own measurement pass rather than being bolted onto this one.
- **An ingest tick re-derives only what changed, and the cursor is allowed to stand still**: the daemon ingests every ~30s, and it used to re-derive *every* session each time — `scan_opencode_sessions(&opencode_db, None)`, with the `since` parameter the function already had passed as `None`. Measured on a copy of the live DB against the live corpus (7,302 `OpenCode` sessions, a 1.2 GB monolith plus 321 shard DBs totalling 6.7 GB): **7.69 s wall, 902 MB peak RSS, 812% CPU per tick**, which at a 30s cadence is ~208% of one core held forever — matching the ~239% the daemon was observed holding. That is the product's own daemon making the machine it measures worse. `meta.session_scan_cursor` now bounds both stores, and a tick that finds one changed session costs **1.50 s wall, 48 MB RSS, 99% CPU** — 5x the wall time, 19x the memory, and ~42x the sustained CPU share (208% of a core down to 5%). A tick that finds *nothing* returns early, before the DB-side passes, and costs **0.26 s / 11 MB**; the ~1.2 s between the two is therefore the per-tick whole-table work this change did not touch (`delete_non_user_message_events`, `import_local_events`, and the attribution passes — the two focus passes each over 2.7 M events), not the corpus scan. That is where to look if the tick needs to get cheaper again. Four properties are load-bearing. **The cursor is captured before the scan and written after the commit**, so a session written mid-scan has a timestamp after the recorded cursor and is caught next pass rather than falling into the gap. **It is read back minus `SCAN_OVERLAP_MINUTES` (5, the margin `tt sync` already uses for `last_sync_at`)**, covering a backwards clock step and the window between `OpenCode` committing a `session` row and its shard receiving the messages that row counts. **It only advances on a scan that actually read everything** — see below. And **writing it must not bump `db_version`**: a cursor changes no event, stream, or assignment, so bumping would fire the daemon's 2s watcher on every tick for nothing.
- **A scan that could not read the store is not a scan that found nothing**: three conditions inside `scan_opencode_sessions` used to present identically as `Ok(vec![])` — the monolith would not open, the session query failed, or a session row would not build. Under a full scan every tick that was harmless, because the next tick re-read everything anyway. Under a cursor it is silent data loss: advancing past a window nobody read means no later pass ever asks for it again, since each pass asks for a *later* `since`. Both scanners therefore return `tt_core::ScanOutcome`, whose `complete` flag distinguishes "nothing changed" from "I could not read it", and `advance_scan_cursor` refuses to move on the latter — it warns and leaves the cursor, which costs one repeated scan of a bounded window and is self-healing. The line between the two is the one the code already drew for logging: a session skipped as **empty** is an expected state (an aborted session leaves nothing to parse) and keeps the scan complete, while anything that warrants a `warn!` marks it incomplete. An **absent** store is complete too — most machines run only one harness, and treating absence as failure would freeze the cursor forever. One cursor covers both stores, so it advances only when both were complete.
- **Incremental scanning shrinks the prune's keep-set, and that is exactly the contract it was written to**: `prune_user_message_events` retires `user_message` rows absent from a per-session keep-set, and leaves sessions *absent from the map* untouched, because a caller can only speak for transcripts it read. An incremental pass supplies only the sessions it re-derived, so the prune does strictly **less** work — never wrong work. It never deletes rows for a session it did not look at; `tt-cli/tests/ingest_incremental.rs` pins that. The real consequence is elsewhere: a change to what the extractor derives now reaches only sessions that happen to change afterwards, so **an extractor change owes a `tt ingest sessions --full`**, which is one of the two reasons that flag exists (the other is a cursor suspected of drifting). That is not theoretical: adding one `INJECTION_MARKERS` entry and running only incremental passes left **2,766 injected `user_message` events alive in the corpus**, because their sessions had not been touched since, and a later `--full` pruned every one of them. Direct time on Jul 20, Jul 22 and the week of Jul 13 was **byte-identical** before and after — the same null result the marker itself produced, since those turns fall inside attention windows other signals already cover — so the reason to run it is correctness of what the database claims happened, not a number anyone will see move. This is the incremental half of the entry above.
- **The Claude path is bounded by file mtime, and its byte-offset manifest is not the mechanism**: `~/.claude` is scanned separately and had the same defect — every JSONL re-read from byte 0 on every tick. `scan_claude_sessions_incremental` now skips a file whose mtime predates `since`, read off the directory entry the walk already holds, so a skipped file is never opened. A file whose mtime cannot be read is parsed rather than skipped: when the filter cannot be evaluated, do the work. Note this path was **not** the cost here — locally `CLAUDE_CONFIG_DIR` points at `~/.dotfiles/.claude`, holding 16 files and 1.3 MB against `OpenCode`'s 6.7 GB — so the fix is about the shape scaling, not about the measured win. A `ClaudeManifest` of byte offsets does exist at `~/.local/state/time-tracker/claude-manifest.json`, but it belongs to `tt export` and is deliberately not reused here: it answers "which *lines* are new", which suits an append-only event stream, whereas ingest re-derives a session's whole summary (prompt list, counts, first/last timestamps) and needs the whole file or none of it. Wiring the manifest into ingest would resume mid-file and produce partial sessions.
- **Keep `.gitignore` `/lib/` anchored**: the leading slash is load-bearing. An unanchored `lib/` (inherited from the Python template) matches any `lib/` at any depth — it silently excluded `crates/tt-server/web/src/lib/**` from version control AND, because Tailwind v4's content scan is `.gitignore`-aware, compiled every utility class used in those components to nothing. Adding any new `lib/` directory? anchor it.
- **No `unwrap()` in non-test code** (except compile-time-safe patterns like `LazyLock` regex, hardcoded `NaiveTime`)
